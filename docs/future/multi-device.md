# 多端架构（电脑 + 手机）

> 状态：方向已定（2026-10-01），实施在双端需求出现时启动。
> 结论：采用「云端内核」方案（模型 A）；缓存 / 离线（模型 C）后置，且按子应用定制。

## 1. 目标与现状

- 未来要在手机上使用 MyOutside，个人数据双端可用；
- 现阶段单机（桌面 Electron，内核本地）继续开发；架构不为多端做提前实现，只保留演进路径。

## 2. 曾经考虑的四种模型

| 模型 | 内核（唯一写者） | 服务在哪 | 数据在哪 | 离线 | 冲突合并 | 复杂度 |
|---|---|---|---|---|---|---|
| A 云端内核 | 云端一台 | 云端 | 云端 | 需后补 | 不存在 | 低 |
| B 本地优先 | 每台设备一个 | 各设备 | 各设备 + 同步层 | 完整 | 需要 | 高 |
| C 云端内核 + 本地缓存 | 云端一台 | 云端 | 云端 + 设备只读缓存 | 读离线 / 写排队 | 轻微 | 中 |
| D 家里设备当内核 | 桌面/家里主机 | 那台设备 | 那台设备 | 看隧道 | 不存在 | 中低 |

## 3. 决定

- **采用 A**：内核与应用后台服务在云端，界面（前端）在本地；设备端 = UI + SDK（走网络传输）。
- **宿主**：作者自租服务器（实施时选型）。
- **缓存 / 离线（C）后置**：缓存是高度按应用定制的（每个应用缓什么、怎么缓存各不相同，例：vocab 缓存待复习卡片 + 排队提交评分），等真需要时按应用逐个补。
- **B 不采用**，但防线保留：坚持「所有写入都过内核」，将来若要变更捕获 / 本地优先，可在内核层加，不动应用代码。

## 4. 落地后的部件分工

| 部件 | 位置 |
|---|---|
| UI（外壳 + 各子应用界面） | 本地（每台设备） |
| SDK / 传输 | 本地；传输从 Electron IPC 换成 WebSocket |
| 内核（队列 / 事务 / 路由 / 迁移 / DataVersion） | 云端 |
| 应用后台服务 | 云端（与内核同处） |
| 数据库 + 文件仓库 | 云端 |
| 设备能力（音频、通知、文件选择） | 本地（始终） |
| 身份 / 登录 | 云端（A 方案的隐性成本，哪怕单用户也要一点） |

## 5. 对当前开发的要求（马上遵守）

1. SDK 与传输保持「可换传输」：调用面（`outside.call`）不假设是否同进程；
2. 设备能力只放 UI 侧（发音、通知、文件选择等不进后台服务）；
3. 内核、契约、应用后台代码保持运行时无关（不 import Electron / 浏览器特有 API）；
4. `kernel-node` 适配器（better-sqlite3 + Node fs）将来在云端直接复用——同一套内核代码，本地（v1）与云端（未来）同构部署。

## 6. 移动端结论

- 手机端 = 同一套 Web UI（PWA / Capacitor 壳）+ SDK；薄客户端，**不需要本地内核**；
- 之前规划的 `kernel-web`（SQLite WASM / OPFS）适配器降级为「B 方案的备件」，A 方案下不需要；
- 缓存（将来的 C）在设备端可以是任意简单存储（IndexedDB 等），不需要 SQLite。

## 7. 待办（多端实施时）

- 服务器选型与部署（Node 服务 + SQLite 文件 + 文件仓库）；
- 身份 / 登录、TLS；
- 传输协议细节（WebSocket 消息格式、断线重连、并发会话）；
- 按应用的离线缓存设计（逐个应用定）。
