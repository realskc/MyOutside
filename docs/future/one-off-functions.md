# 临时函数（one-off functions）技术设计

> 未实现。规则与理由见 D-0001；作者的预期见 `user-spec/principles.md`「需求观」、`user-spec/future/builder.md`。

## 1. 规则落到工程上

| 规则（D-0001） | 工程实现 |
|---|---|
| 软门槛 + 作用域 | builder 发起前向用户展示意图、源码与作用域，用户确认后才执行 |
| 作用域内可直写 | 作用域内的应用：允许绕过其 API、直接读写它们的表（数据库层约束仍然生效）；作用域外：只能 `ctx.call` 对方的 API |
| 自动留痕 | 内核把意图、完整源码、参数、作用域、影响行数、结果（含失败原因）写成一篇 markdown 日志 |
| 无晋升 | 注册是内存态，执行一次后立即注销（无论成败）；要重试就重新注册 |
| 经内核执行 | 走串行队列 + 事务 + DataVersion；内核未运行时不允许直接改库 |

实践建议：能调 API 的地方先调 API，直写只留给 API 表达不了的字段；直写后若应用提供重算 / 修复 API，应调用它恢复不变量。

## 2. 接口（示意）

```ts
// builder 侧的 tool call：注册 → 执行 → 注销 → 写日志，一步完成
oneoff.run({
  intent: "手工修正：把 word#42 的 autoScore 改成 0.9",  // 必填
  source: "<代码字符串或文件路径>",                       // 必填，源码进日志
  scope: ["vocab"],                                       // 允许直写的应用
  params: { wordId: "42", score: 0.9 },
});
// → 事务内执行 → 立即注销 → 日志落盘 → 返回结果
```

对 builder 而言，一次临时函数就是一次 tool call；「永久修改」是另一类需要用户同意的 tool call。

## 3. 技术要点（已验证可行）

- **子应用不可调用**：注册在独立命名空间（如 `#oneoff.*`），`outside.call` 的路由不解析它；
- **执行完消失**：注册是内存态，执行后立即注销；
- **源码留档**：注册时内核读取文件 / `fn.toString()`，写进日志；
- **作用域检查**：直写时校验目标表的归属是否在作用域内，超出即拒绝（需要一个不加前缀、但校验归属的数据助手）；
- **隔离程度**：运行在内核进程里，理论上具备 Node 的全部能力；控制手段 = 软门槛 + 源码留痕 + 用户过目。更硬的隔离（受限子进程执行）见 D-0001「什么时候应该重新考虑」。
