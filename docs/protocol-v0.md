# MyOutside 协议 v0（骨架草案）

> 状态：草案，未定稿。目标是把已确认的决策（见 `requirements.md`）落成可讨论的接口形状。
> 贯穿示例：「对话应用加词 → 学英语应用词库落账」。
> 2026-09-30 修订：确立「边界原则」——跨应用的一切操作与数据访问都经由 owner 的 API 函数；禁止跨应用共用表。

## 0. 世界观

- 一个 **SQLite 数据库** + 一个 **文件仓库目录** = 全部持久状态（数据在库内按应用归属划分）。
- 一个 **宿主进程**（v1：Electron 主进程，本地运行；多端阶段：云端服务器）：路由请求、串行执行事务、强制执行数据归属、持有文件仓库。
- 宿主内核保持**运行时无关**（存储 / 传输经适配层）；多端方向已定为「云端内核 + 本地界面」（见 docs/future/multi-device.md）。
- N 个 **子应用**：各自拥有私有数据与公开 API；跨应用只能调用 API。
- 没有网络协议、没有分布式机制；数据库层面的「并发冲突」在设计上不存在。

```
子应用(Web UI) ──SDK──▶ 宿主：所有权校验 → 串行队列 → 单事务执行 → 提交
   ▲                                      │
   └──── call(API 函数) / 平台 API ───────┘
```

## 1. 核心概念

| 概念 | 说明 |
|---|---|
| App | 子应用，唯一 id（如 `vocab`）；安装即常驻（v1 无启用 / 停用概念） |
| Manifest | 声明：id、名称、UI 入口、后端模块、**数据域（表）**、**公开 API**、协议版本 |
| Data Domain | 数据域：一组表，**归属唯一 owner**（应用或主框架）；非 owner 无法直接访问（硬所有权） |
| API 函数 | 应用（或主框架）对外暴露的功能单元：查询、写命令、事务钩子；**跨应用唯一通道** |
| Transaction | 宿主对一条写操作的执行：所有权校验 + 调用相关 API 函数（事务变体）+ 单事务提交 |
| DataVersion | 全局单调递增版本号，每次提交 +1；子应用激活时比对决定是否刷新 |

## 2. 原则

1. 所有写入经宿主；子应用无法直接接触数据库与文件仓库。
2. 一条写操作 = 一个事务 = 全成功或全失败。
3. 事务内的 API 函数（`tx.call`）是纯函数：只产生对自己数据的读写意图，**不做**文件 / 网络副作用。
4. **边界原则**：跨应用的一切操作与数据访问都通过调用 owner 的 API 函数；**禁止跨应用共用表**；非 owner 的表访问由宿主拒绝。
5. 文件与数据库分离：数据库先提交；文件删除走「待删队列」，由宿主后台惰性执行。**先库后文件，允许孤儿文件，禁止幽灵引用**（详见 §7）。
6. 无推送。刷新模型为「激活时比对 DataVersion」。将来若需同屏实时，在 DataVersion / 提交通知上扩展，不破坏现有协议。

## 3. 事务模型（v0）

「一次事件多处落账」不需要两阶段提交：发起应用的写操作在宿主内被展开为多个 API 函数调用（事务变体），全部同步执行于同一个数据库事务中。

```
App(dialog)                    Host                                 DB(tx)
  │                             │                                     │
  │── call(dialog.captureWord) ▶│                                     │
  │                             │ 校验参数 / 前置条件                   │
  │                             │── dialog 私有表写入 ────────────────▶│
  │                             │── vocab.addWord（事务变体）─────────▶│  vocab 的 API 函数
  │                             │── 提交 ─────────────────────────────▶│
  │                             │ DataVersion += 1                     │
  │◀─ ok({status:"added"}) ─────│                                     │
```

- 跨应用落账 = 调用 owner 应用的 API 函数（事务变体）；每个应用只写自己归属的表。
- 原「客户端提交批次计划 batch」备选**废弃**：违反边界原则。
- 失败：整体回滚，返回结构化错误。

## 4. 接口形状（示意，TypeScript）

### 4.1 Manifest

```ts
interface Manifest {
  id: string;                     // "vocab"
  name: string;                   // 显示名
  protocolVersion: number;        // 与宿主协商
  schemaVersion: number;          // 数据 schema 版本
  ui: { entry: string };          // 子应用 Web UI 入口
  backend?: { entry: string };    // 运行在宿主内的后端模块（私有数据的唯一持有者）
  owns: string[];                 // 数据域归属声明，如 ["vocab.card"]
  api?: ApiDecl[];                // 对外暴露的 API 函数签名（查询 / 写命令 / 事务钩子）
}
```

### 4.2 SDK（子应用可见）

```ts
// 调用 API 函数（任意应用 / 主框架提供）：读与写都走这里
outside.call<Svc>(name: string, payload: object): Promise<Result>;

// 平台信息
outside.apps.list(): Promise<AppInfo[]>;
```

说明：

- 函数的执行类别（读 / 写）由函数声明决定：写函数由宿主放入串行队列、以事务执行；读函数可直接执行。
- **没有通用跨应用查询接口**。读别人的数据 = 调用对方暴露的查询函数（菜单式）。
- 应用自家数据的内部访问（SQL / 类型化封装）属于应用内部实现；宿主可提供薄工具库作为便利，不属于协议。

### 4.3 API 函数（运行在宿主内、由应用的后端模块提供）

```ts
// 事务变体（kind: "tx"）：可被其他应用在事务内调用（纯数据、同步）
defineApi("vocab.addWord", { kind: "tx" }, (ctx, input) => {
  ctx.exec("vocab.card.upsert", { word: input.word, ... });
  return { status: "added" | "merged" };
});

// 读变体（kind: "read"）：事务外调用（异步）
defineApi("vocab.dueCards", { kind: "read" }, (ctx, input) =>
  ctx.queryOwn("vocab.card", { where: { dueAt: { lte: input.before } } })
);
```

### 4.4 两种调用语义（核心区分）

| API | 语义 | 用途 |
|---|---|---|
| `tx.call(name, payload)` | **事务内**：同步、纯数据、与本次写入同生共死 | 跨应用原子落账（加词 → 词库） |
| `outside.call(name, payload)` | **事务外**：异步、无原子承诺 | 普通调用（查询 / 业务操作） |

判断规则：这次调用需要与我的写入同生共死吗？需要 → `tx.call`；不需要 → `outside.call`。

## 5. 错误与回滚

- 校验失败或任一 API 函数抛错 → 整个事务回滚。
- 错误结构：`{ code, app, fn, message }`，可直接展示给用户。
- v0 的纯数据约束下不存在「部分成功需补偿」的情形；将来若引入副作用（文件、网络），必须走补偿 / 后置钩子（post-commit），不得混入事务。

## 6. 迁移与版本

- 每个应用携带 schema 迁移脚本，且**只操作自己归属的表**；宿主启动时按注册顺序执行并记录版本。
- 协议版本不兼容时：宿主拒绝装载该应用并明确提示。
- 迁移也走宿主的单事务模型，失败即回滚，不留半迁移状态。

## 7. 文件仓库

- 布局：`<data>/files/<appId>/<uuid>`；数据库记录 `files.file(id, appId, path, mime, size, sha256, created_at)`。
- 文件同样归属唯一应用，跨应用访问经由 owner 的 API 函数。
- 写入：先落盘临时文件 → 计算校验和 → 数据库事务登记 → 原子改名。
- 删除：事务内只删 / 标记元数据，并写入 `files.pending_delete`；宿主后台任务负责删物理文件。
- 崩溃恢复：启动时清理待删队列与临时文件；孤儿文件允许存在（后续 GC），**幽灵引用（库里有记录、盘上无文件）必须避免**。

## 8. 刷新模型

- 子应用激活（切换 / 打开）时：先比对 DataVersion，变化则重新执行关键查询。
- 可选增强：宿主在提交后给**当前活动面板**发一条轻量通知，省去一次版本查询。
- 将来若支持同屏并排，只需把「通知」从活动面板扩大到可见面板；协议形状不变。
- 跨应用监听（域级失效通知 / 事件总线）**暂缓**：单活动面板 + 激活刷新已覆盖；保留扩展位。

## 9. 待定

1. API 函数的命名与版本策略（随 `packages/contracts` 第一版确定）。
2. 数据域注册细节：表名约定（如 `vocab__card`）+ 归属登记方式。
3. 应用内部数据访问的实现方式（SQL / 类型化封装）——内部自由，宿主可选提供辅助库。
4. 后端模块的加载 / 打包细节（Electron 已定案：宿主主进程内的 Node 模块）。
5. 首批子应用：第一步只做学英语应用（见 docs/apps/vocab.md）；对话应用作为第二步（验证跨应用耦合）。
6. 「临时函数（one-off）」通道的形态（作用域直写、单次执行即消失、自动留痕、由 builder 发起）——见 requirements.md §2.6 / docs/future/one-off-functions.md。
7. 平台 AI 服务的 API 形状与配额模型（`platform.ai.*`；密钥由平台保管）——见 requirements.md §2.8。
8. AI 辅助的写流程模式：异步解析（read 侧，可调用平台 AI）→ 事务提交（tx 侧）两步——首个用例见 docs/apps/vocab.md。
