# MyOutside — 需求与决策记录

> 状态：需求思考阶段
> 本文记录已确认的决策与悬而未决的问题。决策变化时直接更新本文，保持单一事实来源。

## 1. 项目一句话

MyOutside 是一个可移植到 Windows / Linux / macOS 的 GUI 宿主应用：在其中按协议装载多个子应用，界面类似模拟器（宿主 + 面板式应用），子应用之间可以良好、原子地交换信息。

## 2. 已确认的决策

### 2.1 定位与开发方式

- **定位：模块化单体**。MyOutside 是一个产品被拆成多个面板式子应用，而不是插件平台。子应用之间强耦合，但**边界清晰**。
- **边界原则（2026-09-30 追加）**：每个应用 = 私有数据 + 公开 API。
  - 跨应用的一切操作与数据访问，都通过调用对方（或主框架）提供的 **API 函数**完成；
  - 每个数据一定属于且仅属于一个子应用（或主框架），**禁止跨应用共用表**，由宿主强制执行（硬所有权）。
- 耦合手段（详见 protocol-v0 附录 A）：① 共享契约（`packages/contracts`：类型 + zod + 各应用的 API 签名）；② 服务调用（`tx.call` 事务内原子 / `outside.call` 事务外）；③ 事件 / 消息总线暂缓。
- **子应用形态（2026-10-01 追加）**：每个子应用由两个层次构成——**后台服务**（拥有私有数据、对外提供 API，无界面也可被调用）与**前台界面**（Web UI，只经自己的后台 API 访问数据）；应用**安装即常驻**（v1 不引入启用 / 停用概念）。
- 子应用全部由本人开发（不面向第三方开发者），**暂不需要权限沙箱与兼容性承诺**。
- 开发以 AI Agent 为主。因此技术选型与架构优先考虑 Agent 的可迭代性：单一语言、快速反馈环、**约束靠架构机制而不是靠开发者纪律**。
- 子应用形态未固定，允许混合（Web 内容 / 未来进程化 / WASM），呈现层统一为 Web。

### 2.2 运行形态

- **单实例、单窗口**。
- 同一时刻只有**一个活动面板**（子应用），其余为后台标签。
- **无实时推送需求**：切换 / 打开时刷新即可。
- 可选增强：宿主维护数据版本号，子应用激活时比对，避免无谓刷新（见 protocol-v0 §8）。

### 2.3 数据架构（核心决策）

- **宿主是唯一写入者**：子应用不直接访问数据库，统一通过宿主的数据 API。
- **写请求串行排队**：所有写操作在宿主内单队列顺序执行，**冲突在结构上不存在**，不依赖开发者自觉。
- **跨应用原子事务：有且重要**。形态为「一次事件多处落账」（例：对话应用加陌生单词 → 学英语应用词库落账）；实现为：发起方在一个事务内调用各 owner 应用的 API 函数（事务变体，纯数据、同步），宿主单事务提交。
- **硬所有权**：每个数据域（表）注册时归属唯一 owner（某个子应用或主框架）；宿主拒绝一切非 owner 的直接访问；跨应用数据读写一律经由 owner 的 API 函数。
- **操作历史**：不需要审计 / 撤销 / 时间旅行（保留将来引入软删除或事件日志的余地）。
- **大文件**：元数据入库，文件实体放磁盘目录。

### 2.4 技术栈（已定）

- **GUI 框架：Electron + TypeScript**（2026-09-30 定案）。
  - 理由：宿主内核（串行队列、SQLite 事务、契约校验、服务调用）与子应用服务逻辑同住 Node 进程，**单一语言贯穿全部**；better-sqlite3 的同步事务与串行队列天然咬合；`WebContentsView` 是稳定的多面板 API（BrowserView 已废弃）；自带 Chromium 保证子应用 UI 三平台一致；每个面板可开独立 DevTools，Agent 调试友好。
  - 代价：体积 ~100MB+、内存较高、启动偏慢——当前接受。
  - **回退 Tauri 的条件**（任一成立时重新评估）：放弃「宿主内跑 TS 服务」；同屏多面板不再需要且体积 / 内存成为真实痛点。（移动端不走 Tauri，走 Web / PWA / Capacitor 路径，见 §2.5。）
- 数据库：**SQLite + better-sqlite3**（单文件、事务完备、同步 API 与串行队列吻合）。
- 协议 / 类型：**TypeScript + zod**，`packages/contracts` 作为单一事实来源。
- 工程形态：pnpm workspace monorepo；构建工具（electron-vite 等）属实现细节，搭建时定。

### 2.5 平台策略（2026-10-01 定）

- 桌面端 = Electron；**移动端兼容是目标**（关键需求），接受以 PWA / WebView 壳（Capacitor 式）承载同一套 Web UI，不要求原生 app。
- **多端方案 = 云端内核**（模型 A）：内核与应用后台服务在云端，界面（前端）在本地；宿主由作者自租服务器（实施在双端需求出现时启动）。缓存 / 离线（模型 C）后置，且按子应用定制（详见 docs/future/multi-device.md）。
- 宿主内核保持**运行时无关**：存储 / 传输经适配层——`kernel-node`（better-sqlite3 + Node fs）在本地与云端复用；`kernel-web`（SQLite WASM + OPFS）降级为备件（仅在「本地优先」方案下才需要）。
- 子应用 UI 与外壳保持响应式，为移动端布局留空间（单活动面板形态本身接近移动端习惯）。

### 2.6 临时需求与「临时函数」（2026-10-01 修订）

- **立场**：临时需求是一等公民；标准形态是**临时函数（one-off function）**——一段一次性代码，用来表达现有接口表达不了的操作（例：手工修正某个自动计算的字段、批量导入既有数据）。
- **软门槛**：发起前向用户说明并获得确认；确认内容包含**作用域**（这次只允许直写哪几个应用的数据）。
- **作用域规则**：作用域内的应用，允许**绕过其 API、直接读写它们的表**（数据库层的表约束仍然生效）；作用域外一律走对方的 API（`tx.call`）。
- **单次执行**：执行一次后**立即注销**——无论成功或失败。要重试就重新注册（源码已进日志，函数文件可随之删除）。
- **留痕（自动）**：内核自动把意图、完整源码、参数、作用域、影响与结果写进 agent-log（自然语言 markdown 即可）。
- **工程底线（已确认）**：经内核执行（串行队列 + 事务 + DataVersion）；**内核未运行时不允许直接改库**。
- **不设晋升**：临时函数不可永久保留；若要永久化某个辅助函数，必须由 builder 显式发起「永久修改」工具调用并经用户同意（见 §2.7）。

### 2.7 Builder 子应用（2026-10-01 追加）

- MyOutside 将自带一个 **builder 子应用**（agent / chat 形态）：用户用自然语言在其中**建立子应用、修改应用、发起临时需求**（对应 vision 的产品命题——让"每个人都可以自定义应用"成为产品能力）。
- **与临时需求的关系**：一次性函数对 builder 而言就是一次 **tool call**（注册即执行，执行完消失）。
- **与永久修改的关系**：任何要永久保留的辅助函数 / 应用修改，必须由 builder 显式发起**「永久修改」类型的 tool call**，经用户同意后走正常修订流程。
- 实现属于后续阶段（v1 之后）。

### 2.8 平台 AI 服务（2026-10-01 追加）

- MyOutside 维护 **DeepSeek API key**（平台设置项）；**密钥由平台保管，子应用拿不到**。
- 子应用通过**平台 API**（如 `platform.ai.chat`）调用 AI：请求透传 messages / tools，响应（含 tool calls）原样返回。
- 由平台代理调用，将来才能实现**按应用配额、用量统计、更换模型**（暂不做）。
- 密钥存储 v1 存平台设置（SQLite 明文；后续迁系统钥匙串）。
- 定位：平台 AI 是**核心基础设施**——预计多个子应用都会使用（查词、去重判断、未来的对话 / 阅读等）。

## 3. 悬而未决

1. 各应用公开 API 的命名与版本策略（随 `packages/contracts` 第一版确定）。
2. 数据域注册细节：表名约定（如 `vocab__card`）+ 归属登记方式。
3. 应用自家数据的内部访问方式（SQL / 类型化封装）：属应用内部自由，宿主可提供薄工具库，非协议关键。
4. 首批子应用：第一步只做「学英语应用」（Anki 式，见 docs/apps/vocab.md）；「对话应用」作为第二步，用于验证跨应用耦合。
5. 模拟器式界面的具体布局与窗口管理细节（标签 / 侧栏 / 面板切换实现）。

## 4. 非目标（当前阶段明确不做）

- 第三方开发者生态、权限沙箱、协议兼容性承诺
- 实时协同、面向多端的推送
- 多实例 / 多用户 / 跨设备同步
- 完整撤销 / 审计 / 时间旅行
