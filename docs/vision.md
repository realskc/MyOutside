# MyOutside — 产品愿景（核心动机与世界观）

> 本文记录产品的核心动机与世界观。`requirements.md`（决策）与 `protocol-v0.md`（协议）服务于本文。

## 1. 时代背景与核心动机

Vibe coding 让"做软件"的成本降到了前所未有的低点：任何现代、有基本智力、有基本条件的个人，都可以做出自己的软件。

由此得到一个关键推论：**"自己做应用"不再是瓶颈（bottleneck）。**

## 2. 产品命题

MyOutside 要构建的是一套特殊的应用：

- **每个人都可以用**；
- 但**每个人的应用又都不一样**。

它的核心是**子应用**：使用者在 MyOutside 里按协议装载、组合、改造自己的子应用集合，从而得到一套只属于自己的软件。

实现路径：MyOutside 自带一个 **builder 子应用**（Agent 形态）——用户用自然语言在其中建立子应用、修改应用、发起临时需求。

## 3. 最大的特色：两大核心能力

1. **自由定制**：用户可以根据自己的需求自由定制子应用——组成哪些应用、每个应用长什么样、怎么工作，都由自己决定。
2. **强耦合的复合能力**：子应用之间可以相互耦合，在「**生活工作流**」层面爆发出远强于单个应用的能力与便利度。

例如：对话应用里随手记下的生词，自动进入学英语应用的记忆计划——这种跨应用的顺手衔接，就是"生活工作流"层面的价值。

这两点合起来，正是"每个人都可以用、但每个人的应用又都不一样"的具体形态：**定制让它变成"你的"，耦合让它变得"强"。**

## 4. 耦合哲学：Agent 时代的工程观

- 子应用之间**可以相互耦合**（互相调用功能、互相交换数据）——这是功能的需要，也是产品的价值。
- 但耦合**不代表新建 / 删除 / 修改子应用的代价大**：在硬边界协议下，每个应用有清晰的私有数据与 API 面，让 Agent 修补子应用之间相关部分"轻而易举"。
- 高度解耦曾经是**团队规模的产物**——为了让一整个团队共同维护一个项目更方便。在 Agent 时代、个人软件的场景里，**不再需要为此付出设计代价**。
- 结论：**拥抱耦合，但保持"可变更"**。硬边界的意义不是隔离，而是给 Agent 的修补工作提供明确的定位点。

**这套哲学同样适用于"安装"：Agent 适配，而不是依赖解析。** 安装别人写的子应用，不需要机械的依赖解析（那是上一个软件工程时代的思维），而是让 Agent 做本地化改造：

1. **剥离**：清除新应用中引用"你没有的子应用"的部分，保留主干功能；
2. **重连**：扫描当前用户已有的全部子应用，发现可以建立的连接（集成机会），并主动建议、生成适配代码——把"别人的应用"改造成"你的应用"。

这得益于硬边界协议：耦合点都是显式的 API 调用（契约可见），Agent 才能精确定位、剥离与重连；适配代码不需要预先设计架构，可以在安装时生成。

## 5. 需求观：一次性需求与「临时函数」

- Agent 时代，用户会"一拍脑袋"提出一次性需求（例：批量导入 2000 个已掌握单词、手工修正某个自动计算的字段）。这类需求不值得都做成产品功能。
- 传统做法：靠固定接口抵御临时需求——要么提供通用接口，要么直接拒绝。
- **本项目的立场：认可「让 Agent 临时在应用现有接口之外直接完成一件事」是合理的**——标准形态是**临时函数**：一段一次性代码，限定作用域、执行一次、自动留痕、立即消失。
- 三个配套机制：
  1. **软门槛**：发起前经用户确认，确认内容包含**作用域**（只允许直写哪几个应用的数据）；
  2. **自动留痕**：意图、完整源码、参数与结果由内核自动写进日志（自然语言即可）；
  3. **无晋升**：临时函数不可永久保留；永久化只能由 builder 显式发起「永久修改」并经用户同意。
- 边界：临时函数依然遵守平台底线（经内核执行；工程形式见 requirements.md §2.6、docs/future/one-off-functions.md）。

## 6. 分发与演进路线（暂定）

- **阶段 0（现在）**：只有作者一个人使用。
- **阶段 1**：如果好用，分发给身边的朋友——每个人可以有自己的应用组合。
- **阶段 2**：上线部分平台能力：
  - 提供**先验偏置、框架**（脚手架、模板、范式），降低新子应用的开发成本；
  - 让"安装别人写的子应用"变得容易——按「Agent 适配」的方式（见 §4 耦合哲学）。

## 7. 对当前设计的要求（映射）

- 子应用必须**创建成本低、删除成本低、修改成本低** → 协议要为 Agent 的可修补性服务（清晰的 API 清单、契约即文档）。
- 硬边界（私有数据 + 公开 API）是这段愿景能成立的前提之一 → 见 requirements.md §2.1、protocol-v0 §2 原则 4。
- 一次性需求不做成功能，由临时函数完成 → 需要软门槛、作用域与自动留痕（见 requirements.md §2.6）。
- 当前是单用户阶段 → 不做权限沙箱、不做版本兼容承诺（见 requirements.md §4 非目标）。

## 8. 未来要重新审视的问题（届时再处理）

- 「Agent 适配安装」的工程形态：耦合点扫描、剥离与重连的流程与验证方式。
- 「临时函数」通道的具体工程形式（软门槛与作用域确认、日志规范、与内核不变量的关系）。
- 跨作者应用的版本与兼容问题（协议版本协商、API 破坏性变更）。
- 信任与权限边界（别人写的子应用对你的数据意味着什么）。
- 平台能力的具体形态（先验偏置 / 框架以什么粒度提供）。
