# 66CCFF-0011 分轨静音 / 独奏 / 音量用 Web Audio 音量节点，`<audio>` 本身永远不静音

- 状态：有效
- 日期：2026-11-08
- 决策者：讨论（作者同意这个修法；具体实现由 agent）
- 取代：[66CCFF-0002](66CCFF-0002-in-app-slow-player.md) 中「分轨音量 / 静音 / 独奏」直接用 `<audio>` 的 `muted` / `volume` 的做法
- 服务于：
  - 作者预期：[`../README.md`](../README.md)「内建播放器：分轨音量 / 静音 / 独奏」
  - 上游决策：[66CCFF-0002](66CCFF-0002-in-app-slow-player.md)（多个 `<audio>` 同步播放六轨，主轨校正其它轨）

## 背景

播放器用六个 `<audio>` 同步播放六轨；第一条有的轨（通常是人声）是主播放器，其它轨和它差出 0.12 秒以上就被拉回到它的时间（`ui/ui.js` 的 `onTimeUpdate`）。原来静音 / 独奏直接设 `<audio>.muted`，音量直接设 `<audio>.volume`。

## 决策

- 每个 `<audio>` 经 `createMediaElementSource` 接进同一个 `AudioContext`，后面跟一个 `GainNode`；静音 / 独奏 / 音量只改音量节点（静音 = 音量 0，约 15 毫秒的渐变）。
- `<audio>` 的 `muted` 永远是 false、`volume` 永远是 1。
- 点播放（或按空格）时启动音频上下文（`resume()`）。
- 实测：在 Electron 38 里，`app://` 页面把 `media://` 的音频接进 Web Audio，不需要 `crossOrigin` 和 CORS 响应头，也能拿到真实数据（试过加 / 不加，结果一样），所以没有加。

## 考虑过、没有采用

- **静音时把 `<audio>.volume` 设成 0，而不是 `muted`**：桌面版 Chromium 目前不会因此暂停，但这依赖一个内部开关（`kPauseMutedBackgroundAudio` 在安卓上默认打开，桌面上默认关闭），随时可能变。
- **主播放器改选一条没静音的轨**：独奏切换、全部静音时都要重新选，且只是绕开，不是不再触发。
- **切回窗口时按「跑得最远的那条轨」重新对齐**：还是让浏览器暂停了某一轨，只是事后补救。

## 代价

- 播放链路多了一层 Web Audio；音频上下文需要在用户操作时启动。
- 将来如果 Electron 把 `media://` 当成跨源、对 Web Audio 只给静音，六轨会全都没声音（冒烟检查会报出来，见「修复的 bug」）。

## 什么时候应该重新考虑

- 播放器整体改成别的方式（例如把各轨解码进同一个 Web Audio 时钟、不再用 `<audio>`）；
- Chromium 改了后台暂停媒体的规则。

## 修复的 bug

- **现象**（Mac 用户上报，2026-11-08）：在纯蓝里播放，切到别的窗口，再切回来，播放进度回退到刚切出去的时候附近。前提是：主播放器（人声）从开始播放起就是静音的（播放前就静音了人声，或独奏了别的轨），并且窗口真的被隐藏了（最小化、切到别的桌面或全屏应用；只是点了别的窗口、纯蓝还露着一部分不算）。不是 Mac 独有，Windows 上最小化应该也会。
- **原因**：Chromium 把「从开始播放起就静音」的纯音频 `<audio>` 当成没有声音，页面隐藏时为了省电把它暂停，页面重新显示时再从暂停处接着播（`WebMediaPlayerImpl::ShouldPausePlaybackWhenHidden`、`HasUnmutedAudio`）。主播放器停在隐藏的那一刻，其它没静音的轨照常往前走；切回来后主播放器接着播，下一次对齐就把其它轨全拉回到旧位置。
- **为什么原来的做法会出 bug（重构时不能再用）**：
  - 不能用 `<audio>.muted` 实现分轨静音 / 独奏：浏览器会在后台暂停这样的播放器；
  - 只要还是「其它轨跟着主播放器对齐」，主播放器就绝不能是一个可能被浏览器暂停的东西。
- **怎么验证修好了**：冒烟测试 `[smoke] 66CCFF background`：给测试曲目造六条静音的轨，独奏第二轨（主轨因此被静音）后播放，把一个看不见、不抢焦点的小窗口真的隐藏 3 秒再显示，检查六轨都在 4.5 秒以后且彼此对齐。修之前这项失败（六轨都被拉回到约 2.9 秒），修之后通过（约 5.7 秒）。`[smoke] 66CCFF web audio` 检查接进 Web Audio 的 `media://` 音频真的有数据。
