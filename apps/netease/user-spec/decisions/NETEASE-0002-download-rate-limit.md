# NETEASE-0002 下载的硬性限制：应用内排队，相邻两首随机隔 10–20 秒，每天最多 50 首

- 状态：有效
- 日期：2026-11-11
- 决策者：作者（间隔和上限的数字、目的）；agent（实现方式）
- 服务于：
  - 作者预期：[`../README.md`](../README.md)「下载」：相邻两次下载之间间隔 10–20 秒的随机时间，每天最多下载 50 首，防止高频连续下载被官方封控；实现方式随意（例如在应用内部排队）
  - 部分取代：[NETEASE-0001](NETEASE-0001-search-and-download.md) 的「每次下载记一条记录」——现在只记真正下载了的

## 决策

### 在后端排队

- 限制做在后端的下载流程里，不靠界面：界面怎么点、开几个窗口，都绕不过去。
- **一次只下一首**：每首下载在应用内部排一个位置，前一首结束（成功、失败或取消）才轮到下一首。
- **间隔**：一首结束后，随机取 10–20 秒（均匀分布），下一首要等到那之后才开始向网易云发请求。
  - 不论成败都算：失败的那次也已经向网易云发了请求；
  - 文件夹里已有、没真正下载的也算（也查了详情、要了下载地址）。
- **重启也算**：第一次用时，按最近一条下载记录的时间加一段随机间隔，推算下一首最早什么时候开始。重启 MyOutside 不会马上连着下。
- 排队和等待时发进度事件：`排队中：前面还有 N 首`（带 `queued`）、`等 S 秒再开始`（带 `waitUntil`）。界面据此显示倒计时，可以取消；取消马上返回，不发请求。

### 每天最多 50 首

- 「今天」按本地时间，从零点算。
- 只算**真正下载了的**：文件夹里已有、跳过的不算。为此**下载记录只记真正下载了的**（取代 NETEASE-0001 里「每次都记一条」），每天的额度就是数今天的下载记录。
- 发起时查一次，排到时再查一次（前面排队的可能已经用完了额度）；满了就报「今天已经下载了 50 首，明天再来」。
- `getStatus` 返回今天下了几首、上限、下一首最早开始的时间、排队的数量；界面显示「今天已下载 x / 50」，满了就不能点下载。

## 考虑过、没有采用

- **在界面里限制**：别的入口（以后纯蓝、命令行）就绕过去了；作者要的是硬性的。
- **间隔按开始时间算**（两首开始之间隔 10–20 秒）：一首无损要下一会儿，按开始算会让「下完马上开始下一首」。按结束算更保守。
- **加一列记「是否真正下载」**：可以，但内核的迁移没有加列，要用原样执行 SQL 的逃生口；记录本来就只该记真正下载的歌，不需要这一列。

## 代价

- 一次点很多首，要一首首等：50 首最少要 8–17 分钟。
- 间隔和排队只在内存里；同一台电脑开两个 MyOutside 不会互相知道（单实例锁本来就不让开两个）。
- 文件夹里已有的歌不进「最近下载」。

## 什么时候应该重新考虑

- 作者调整数字，或者被封控过、觉得还不够保守；
- 要支持批量下载（例如整张歌单）。

## 怎么验证

- 单测：两首同时点，第二首在第一首下完后至少等满间隔才开始查询，进度里有「排队中」和倒计时；重启（同一个数据库文件）后按最近的记录等间隔；等待时取消马上返回、不发请求；每天上限满了拒绝，已有文件不占额度，第二天又能下。
- 冒烟 `netease`：`getStatus` 的上限是 50，界面显示额度。
