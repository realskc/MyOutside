# DIALOG-0018 生成出错中断（例如断网）时，保存已生成的部分

- 状态：有效
- 日期：2026-10-27
- 决策者：讨论（作者选了方案 B）
- 服务于：
  - 作者预期：[对话 user spec「定位」](../README.md)（主力对话工具）
  - 上游决策：[DIALOG-0017](DIALOG-0017-keep-partial-reply-on-stop.md)

## 决策

- 输出到一半出错（例如断网）：照旧按指数退避重试这一轮（最多 2 次，从头重新请求）；重试前通知界面丢掉这一轮已显示的半截，避免新旧文字接在一起；
- 重试都失败时：如果已经输出过文字，把已完成的各轮（搜索过程）与最后一次收到的半截保存为一条回复，记下出错原因（`message.error`），界面标「已中断」，悬停可看原因；可以重新生成；
- 一个字都没输出就失败：和以前一样不保存，显示错误与「重试」；
- 保存下来的回复和普通回复一样进入之后的对话历史（与 DIALOG-0017 相同）。

实现要点：平台 AI 的流式请求中途出错时照常报错，已收到的部分放在错误的 `details.partial` 里；工具循环在重试前推送 `round_retry` 事件，重试都失败时把最后的半截作为最后一轮保留。

## 考虑过、没有采用

- 只修界面、失败时仍然全部丢弃（方案 A）：断网时已经搜索和输出的内容白费；
- 断网后让模型接着写（方案 C）：DeepSeek 的「对话前缀续写」（Beta）可以严丝合缝地接着写，但实测它不能与工具调用同时使用（请求带 `tools` 或历史里有工具调用都会 400），联网搜索打开时用不上；另一种做法是补一句「请接着写」。断网不常见，暂不做。

## 代价

- 重试是从头重新请求这一轮：断在中途时，已收到的部分会被重新生成一遍（多花一点 token），而且重新生成的内容可能和之前不一样。

## 什么时候应该重新考虑

- 断网中断变得常见、或者回复很长时（考虑断了接着写）；
- 其余细节随时可以。
