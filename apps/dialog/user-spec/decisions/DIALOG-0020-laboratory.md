## 背景

作者想做实验：调整一次对话请求中的一切，包括 system prompt、任意历史消息、工具与模型参数，再原样运行并查看模型返回的原始结果。普通对话的规则——树形历史、只能编辑用户消息、固定 deepseek-flash——不适合做这种实验，也不应该被实验需求改掉。

## 决策

- **实验室是对话应用里的一个独立页面**（`ui/lab.html`），不新增 app。普通对话的界面与规则不变；顶栏加一个「实验室」入口。
- **请求体 JSON 是唯一真相**：`messages` 里可以写 system / user / assistant / tool 任意消息，可以有多条 system、可以放在任意位置；`tools`、`model`、`temperature`、`reasoning_effort` 等字段直接编辑。运行 = 把编辑框里的 JSON 原样交给 `platform.ai.chatRaw`，平台不偷偷加日期、搜索说明或截断。
- **响应原样看**：正文、思考、`tool_calls`、usage、finish_reason、原始 JSON 都展示；上游错误也展示完整错误体。可以把选中的 assistant 消息（可以先在请求体里编辑）加入 `messages`，再补 user / tool 消息继续运行。
- **v1 不自动执行工具**：模型返回 `tool_calls` 只展示，工具结果由作者手动填写。这样才是「请求体中的一切」；自动工具循环留给普通对话 / 哲野试验台那类工具。
- **每次运行都存**：`app_dialog__lab_run` 保存完整请求、完整响应（失败时是错误体）、状态（ok / error / aborted）、错误、model、usage、估算花费、用时、来源对话/消息。失败的运行也存；前端关掉页面也不丢。
- **运行在后端**：`dialog.labRun` 是普通的异步函数，调用 raw API 后经事务 API `dialog.saveLabRun` 落库；取消时存为 aborted。
- **从对话导入**：`dialog.getRequest` 导出某个用户消息对应的真实请求（system prompt、展开后的历史、工具、参数），导入实验室后随便改；原对话不受影响。生成与导出共用同一个 `buildConversationRequest`，避免两套逻辑。
- **v1 范围**：非流式；JSON 编辑器 + 渲染预览；不做结构化消息编辑器、多实验线程、请求预设、自动执行工具。`dialog.getRequest` 导出的 body 是 DeepSeek 原生 snake_case，`stream = false`。

## 考虑过、没有采用

- **普通对话加「实验模式」开关**：规则随开关变化，日常对话容易被误改，编辑与发送的流程也会打架。
- **在消息树里允许编辑助手消息**：无法表达任意 system / tool 消息，而且「改一条、后面全部重放」的版本管理比运行记录复杂。
- **单独一个实验室 app**：可以单独统计用量、也可以给别的应用用；但要新注册 app、把 dialog 的请求接口公开，v1 不值得。以后需要时再拆。

## 代价

- 没有树形分叉；版本就是运行记录。每条运行都存完整请求，会有重复存储（实验阶段可以接受）。
- 用纯 JSON 编辑长对话比较累；以后觉得难用再加结构化消息视图。
- 实验花费记在对话应用名下，不能单独看「实验室」花了多少。

## 什么时候应该重新考虑

- 作者觉得 JSON 难用 → 加结构化消息编辑器；
- 想选择导入哪一条用户消息，而不是默认最后一条 → 导入面板加消息选择；
- 需要同时管理多个实验 → 加 `lab_session` / 实验线程；
- 需要自动执行工具 → 在实验室里接工具循环；
- 想把实验结果写回对话 → 加「应用到对话」；
- 需要单独统计实验室用量或给其他应用用 → 拆成独立 app；
- 需要流式 → 扩展 raw API 与实验室的显示。
