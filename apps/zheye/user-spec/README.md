# 哲野（zheye）

> 这是哲野自己的作者预期。技术文档见 [`../docs/README.md`](../docs/README.md)；决策见 [`decisions/`](decisions/README.md)。

命名：取「之乎者也」，与知乎相呼应；意取「哲理的海洋 / 知识的原野」。

一句话：**把「一个点」讲透的个人讲解系统——你提出想学的东西或投递材料，内容为学会服务。**

下面的「目的」「愉悦」「角色」是作者的高层设计理念（2026-10-27 作者确认）。

## 目的

- **最高目的**：让用户把「一个点」学进去——低认知压力，同时真正学到东西。判断标准不是精炼、不是长短，而是**把被讲的点讲好、讲透**。
- **第二目的**：投递了材料时，至少把原文的核心内容和总标题讲到（总标题说了什么，就要讲清楚什么）；不要求把原文全部讲完整（以后可能加档位：把原文讲到什么程度）。没有材料的请求（例如「给我讲讲 DeepSeek Harness」）不存在覆盖原文的问题。
- 两者冲突时，最高目的优先：**宁可少讲几个点、每个点讲透**，也不做平均用力的逐节笔记。

## 愉悦

- 哲野要带来的是**学到真东西的愉悦**——顿悟、理顺、看清结构——同时不累。
- **不做**：投其所好、性格或口味画像、强行加笑话或个人关联。

## 角色

- 愿景：**替代刷信息流**（知乎、B 站）。放松的动机保留，但获得的始终是自己想学的高质量内容。

## 真实性

- **硬约束：不编造；推测不能当成定论。**
- 但**不要求**对原文逐句忠实：文章是精读的成果，允许重构、综合、补充背景。
- 讲解时 AI 要**主动搜集资料**（联网搜索，见 [ZHEYE-0014](decisions/ZHEYE-0014-web-research.md)），不能全凭自己的知识。

## 讲解风格

- 不强行使用某种语气（例如刻意俏皮）；
- 不大规模地做防御性陈述（「叠甲」），例如动不动就说「但这不代表……」；
- 不强行联系两个本来没有联系的事物；
- 其他要求作者想到了再加。

## 讲解的对象与方法（重新讨论中）

讨论顺序：① 讲解三类内容的方法论（当前）→ ② 机制：流程设计、复用、询问作者前置知识（早期的前置检查要保留，届时讨论）→ ③ 实现上的大障碍与大决策。

**讲解的对象分三类**：

- **概念**：一个普遍存在、非常重要的东西；不一定有常见的名字（很多只在学术领域有名字）。是**一类**东西，能举出很多个例子。例：通货膨胀、强化学习里的训推不一致问题。
- **断言**：某一句话，能判断对不对。例：「信息流会让人上瘾」。
- **实体**：一个具有许多独特属性的事物，是**某一个**具体的东西。例：DeepSeek Harness、Blackwell 架构；一篇论文、甚至一条新闻也可以是一个实体。暂时不单独设「事件」类（不代表以后不会）。
- 概念与实体之间没有很硬的边界，但大部分时候能区分开。
- **同一个东西可以既当概念讲一次，又当实体讲一次**，两者不冲突、侧重点不同，有些重合也没关系。例：Transformer 当实体讲，讲它具体的结构、发展的历史、变体（如 ViT）；当概念讲，讲它的重要特点（可以 scaling、归纳偏置低）、与其他概念的关系（如 ViT 与 ResNet 的对比）、与当今世界的关系（大家仍在研究稀疏注意力）。方法、算法这类「做法」也这样处理。

**讲解概念**：重点在于**为什么会抽象出这个概念**。

1. 先通过具体例子，引出这个概念的重要性或常见性；
2. 再用例子讲若干条与这个概念相关的直觉——直觉就是这个概念与其他事物的联系，几乎就是断言；**希望这些直觉与「断言」这一类有联系**（具体怎么联系，在讨论机制时再定）；
3. 完全讲完之后，用一些精炼的结论收尾，帮助记忆——就是让 LLM 讲解一个东西时它最容易说出来的、像百科里会有的那种话；**前提是这些话在前面都已经讲明白了**，不能凭空出现新的浓缩结论。

此外，讲概念还要关心**它与世界的关系**：这类东西有什么用、和当今世界有什么联系。

**讲解断言**：

1. **先确保前置知识**：断言中提到的概念、以及理解断言必须用到的概念，用户都已经理解；不理解的，先讲解前置概念；
2. **阐明断言的背景**：交代断言的适用场合，把它变成一个更长、更精确的版本；再用一个具体例子，让用户对断言形成直观感受；
3. **讲解这句话为什么成立**：机理、原因、分析性的解释；
4. **多次微调，形成更强的直觉**：例如稍稍改变断言中的某个要素，解释结论为什么会变、或为什么不变；找一些断言不适用的例子或场景；结合理论的发展史，讲更多相关且有价值的东西；等等。

断言不需要收尾：它本身就是结论。

**讲解实体**：

1. **清楚地解释实体的形态 / 形式**：这一步非常重要，也可能很费劲——一个新产品往往是一种还没有被定义过的东西，很难一句话说清。例：今天给一个人讲 MyOutside 是什么，说「AI 平台」「基于 vibe coding 的子应用平台」，听的人都会一头雾水。所以这一步要用足够具体、足够清晰的词语，把这个实体到底是什么讲清楚，可能会很长；新产品没有一两个词的简介定义是正常的。**不要给一个让人一头雾水的概述。** 这段话里也要带上一些能直接讲出来的特点。例：讲 MyOutside 时，说它装在自己电脑上、里面有背单词、和 AI 聊天、下围棋等各自独立的小程序，同时说出「这些子应用之间可以互相调用接口、形成联系（例如对话调用学英语）」这样的特点。
2. **解释它的意义**：它的新颖点、价值、目标、发明它的原因等；新闻事件则是相关背景；
3. **讲解它本身**：用用户理解的内容讲这个实体本身的特点，能讲明白多少是多少；**不要为了多传递信息而牺牲易读性**；
4. **横向对比**：讲它和一些类似的东西的区别、异同，目的是让用户对它形成更清晰的定位；**不要强行找东西来对比**；
5. **收尾**：列举它的一些特点，帮助记忆；**前提同讲解概念：这些特点在前面都已经讲明白了**，不能凭空出现新的。

讲实体不必刻意讲它与世界的关系，可以只讲这个东西本身的特点（新闻、新产品这类自然会讲到与世界的关系，不是刻意不讲）。

## 长期积累

- **写过的文章长期保存，以后直接复用**：以后学别的东西时，需要的前置如果曾经写过，就直接用那一篇，不再重写（实现见 [ZHEYE-0011](decisions/ZHEYE-0011-reuse-prerequisite-articles.md)）。
- **哲野记住作者对每个概念的了解情况**：问过一次「了解吗」，以后不再问（实现见 [ZHEYE-0012](decisions/ZHEYE-0012-remember-known-concepts.md)）。这是关于作者知识状态的任务数据，与「愉悦」里否掉的口味画像是两回事。了解程度会随时间变化的问题，先做出一版再解决。

## 工作流与提示词由作者把关

- 三类讲解（概念 / 断言 / 实体）的工作流与提示词，**作者要亲自把关，甚至亲自设计**；agent 不能自行定稿。
- 因此哲野目前处在**讨论设计**的阶段：讨论的结论沉淀进本 spec 与决策，离实现还很远。
