# 贯穿全局的原则

## 耦合哲学：Agent 时代的工程观

- 子应用之间**可以相互耦合**——互相调用功能、互相交换数据。这是功能的需要，也是产品的价值（见 `product.md`「强耦合的复合能力」）。
- 但耦合**不代表新建、删除、修改子应用的代价大**：每个应用都有清晰的边界——私有数据与公开的 API 面——让 Agent 修补子应用之间的相关部分轻而易举。
- 高度解耦曾经是**团队规模的产物**：为了让一整个团队共同维护一个项目更方便。在 Agent 时代、个人软件的场景里，不再需要为此付出设计代价。
- 边界的意义不是隔离，而是**给 Agent 的修补工作提供明确的定位点**。
- 因此：子应用必须**创建成本低、删除成本低、修改成本低**。

## 安装：Agent 适配，而不是依赖解析

安装别人写的子应用，不需要机械的依赖解析（那是上一个软件工程时代的思维），而是让 Agent 做本地化改造：

1. **剥离**：清除新应用中引用"你没有的子应用"的部分，保留主干功能；
2. **重连**：扫描当前用户已有的全部子应用，发现可以建立的连接（集成机会），主动建议、生成适配代码——把"别人的应用"改造成"你的应用"。

这依赖于清晰的边界：耦合点都是显式的调用，Agent 才能精确定位、剥离与重连；适配代码不需要预先设计架构，可以在安装时生成。

## 需求观：一次性需求是合理的

- Agent 时代，用户会"一拍脑袋"提出一次性需求（例：批量导入 2000 个已掌握的单词、手工修正某个自动计算的字段）。这类需求不值得都做成产品功能。
- 传统做法是靠固定接口抵御临时需求：要么提供通用接口，要么直接拒绝。
- **MyOutside 的立场：让 Agent 临时在应用现有接口之外直接完成一件事，是合理的。**
- 但这种操作要**用户知情**、**事后可追溯**，并且**不会悄悄变成永久功能**——永久性的修改必须经用户同意。具体形态（临时函数）见 [D-0001](decisions/0001-one-off-functions.md)。

## 约束：软约束与硬约束都要

开发以 AI Agent 为主；将来的用户也通过 builder（Agent）编写应用。对 Agent 行为的约束，两种都要：

- **软约束（prompt、规范、user spec 等）非常重要**：Agent 服从指令的能力已经很强，很多难以硬性限制的约束只能靠它表达。
- **硬约束（框架层面的安全约束）同样重要**：能在框架层面做的硬性安全约束，就应该做。MyOutside 应当**在内核框架和 agent 框架层面**就对 builder 的行为边界进行限制。
- 硬约束是**用户能自由享受 vibe coding 的保底**：即使 Agent 没有遵守软约束，用户的数据与应用也不会因此受到严重破坏。

## 统一的内核让 agent 更安全

- **应用的 API 就是 agent 的工具**：子应用对外提供的功能，可以很好地直接包装成 agent 能使用的工具，不需要另起一套。
- **内核管控 agent 能使用的工具**：agent 能调用什么，由内核检查，而不是只靠提示词约束。
- 因为内核带来了统一性——所有调用都经过内核、API 形式统一、数据都在内核管理之下——**MyOutside 的 agent 框架可以比现有的通用 agent 框架更安全**。具体要做到多安全，作者仍在考虑（见「未定」）。
- 实现见 [D-0049](decisions/0049-agent-layering.md)、[D-0052](decisions/0052-agent-execution-modes.md)、[D-0053](decisions/0053-kernel-enforced-call-permissions.md)。

## 新的 vibe coding：user spec

- vibe coding 的循环（人提需求 → agent 实现 → 人反馈 → agent 调整）**局部收敛、全局漂移**：人的预期没有被显式沉淀，agent 分不清"用户关注的重点"和"自己选择的实现"。
- 需要一层显式维护的 **user spec**：
  - 对 agent，它是**变更许可边界**——spec 之内要动必须回来讨论，spec 之外可以大胆推翻、重构；
  - 对人，它是**重读自己的入口**——忘记产品定位或想法时翻它，而不是翻文档。
- 它是**源**，技术文档和代码是派生物；冲突时以它为准。
- 本项目自身的开发也遵循这一点（即本目录，见 `README.md`）；它同时是 MyOutside 将来要提供给用户的能力（见 `future/user-spec.md`）。
- **只看 user spec 就能重构项目**：项目是 user spec 的一种代码实现。兼容旧版本的代码在这个实现之外——agent 只看 user spec，不知道哪些兼容代码是必要的、哪些不是，这违背了这个构想。所以兼容性要求也要写进 user spec（放在哪、怎么写，还在讨论，见「未定」）。
- **user spec 是一套维护方案**（作者，2026-11-11）：
  - 它可以在刚开始一个项目的时候把地基打好，但绝不是用来凭空造出一个房子的。
  - 刚开始设计项目的时候，作者也没有多少想法；**user spec 的容量和作者的想法成正比**。在这个框架下，**agent 绝不会凭空在 user spec 下创造东西**。
  - 像 superpowers 那种给一套方法论、然后就让 agent 放飞自我的做法，与 user spec 完全相悖（见 [references/Superpowers-thoughts.md](../references/Superpowers-thoughts.md)）。
  - 作者觉得这套范式非常好：user spec 和 reference 能不断沉淀作者的想法、要求和与项目相关的客观事实，不仅越开发越顺，切换 agent 也不会产生太大问题，上下文都在。作者这样设计的目的正是：一个没有前情的 agent 读一遍，就能分清哪些是作者的意志、哪些是可以推翻的实现选择，并看懂每一步是为了什么（作者，2026-11-13）；这套框架已经迭代了一段时间，作者觉得现在的这些边界都挺好，也很喜欢（作者，2026-11-11）。作者把它写成了一个通用的 skill，放在本机 `~/Skills/user-spec/`，不在本仓库（作者：它和 MyOutside 理论上没有关系，但是同一个脉络）。

## 未定

- **兼容性要求写在哪、怎么写**：例如把所有兼容性要求写在某个文档或 spec 目录里。将来发行时，可能还需要把稳定版 / 发行版的具体行为接口存档，以便之后写兼容逻辑。现在没有这方面的需求，等真的要兼容时再定。候选做法（agent 提出，作者觉得听着还行）：
  - 单独一篇 `user-spec/compatibility.md`，集中记所有兼容要求，各应用分节；每条写清要兼容什么、为什么、到什么时候可以删；代码里的兼容逻辑在注释里引用对应条目，删掉条目就删对应代码；
  - 发版时把公开 API 的格式、数据库表结构、清单格式与协议版本、数据目录布局导出成冻结的快照（例如 `releases/v1.0/`），兼容要求指向快照，兼容逻辑照着它写和测试。

- agent 框架具体要做到多安全（利用内核的统一性能做到很多，但要不要做到非常安全，作者仍在考虑）。

以下问题在愿景中提出，留待将来重新审视：

- 「Agent 适配安装」的工程形态：耦合点扫描、剥离与重连的流程与验证方式。
- 跨作者应用的版本与兼容问题（协议版本协商、API 破坏性变更）。
- 信任与权限边界：别人写的子应用对你的数据意味着什么。
- 平台能力（先验偏置 / 框架）以什么粒度提供。
