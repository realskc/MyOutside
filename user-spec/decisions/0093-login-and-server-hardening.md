## 决策

**没登录时能碰的东西压到最少**：只有登录页、提交登录、一次性的设置链接，以及界面的静态文件。其他所有东西（WebSocket、调用、数据）都要先登录；WebSocket 还要检查请求来自 `https://myoutside.org` 的页面（防别的网站借用户的登录状态连进来）。
- 界面的静态文件（外壳和子应用的 HTML / JS / CSS）不要求登录：它们是公开仓库里的代码，不含任何数据；而且沙箱里的子应用页面是「无名源」，带不上登录 cookie（D-0090），要求登录的话页面根本加载不出来。所有数据都经 WebSocket，必须登录。

**处处限大小**：

- Caddy 先挡掉超大的请求：登录和设置链接的请求超过 4 KB 直接拒绝，到不了程序；
- 程序里：用户名不超过 64 个字符、密码不超过 256 个字符，超了在做任何处理（包括算哈希）之前就拒绝；
- 登录以后：WebSocket 每条消息不超过 1 MB。

**限次数，但不为难人**（作者：人类还是很笨的，输错 20 次也可能是正常人类）：

- 同一地址 + 同一用户名：前 10 次输错不用等；之后每错一次，等待翻倍（1、2、4…… 秒），最长 1 分钟；登录成功清零；
- 账号永远不锁：不然别人故意输错就能把用户关在外面；
- 防火墙只封明显是程序的地址：同一地址 10 分钟内输错 100 次以上，或 10 分钟内试了 20 个以上不同的用户名，封 1 小时（fail2ban，和防 SSH 爆破同一个工具）。

**密码与登录状态**：

- 密码存加盐的慢哈希（Node 自带的 scrypt），不存明文；同时算哈希的数量有上限，防止有人靠大量登录请求把 CPU 吃满；
- 登录状态是一个随机令牌，放在 `__Host-` 前缀的 cookie 里（只走 HTTPS、脚本读不到、子域名改不了），服务器只存它的哈希；有过期时间，退出登录即作废；
- 第一个账号用一次性设置链接设密码：链接里是随机长令牌，24 小时过期，用一次就作废；密码由作者在浏览器里自己输入，不经过命令行和对话。

**服务进程关在低权限里**：

- 用专门的 `myoutside` 系统账号运行，只能读写自己的数据目录；用 systemd 的沙箱选项（不能提升权限、系统目录只读、看不到家目录、独立的临时目录、限内存）；
- 只监听 `127.0.0.1`，外面只能经 Caddy 进来。

**密钥**：用户的 API key 加密后存进他自己的库；加密用的主密钥是只有 `myoutside` 账号能读的文件；日志里不出现 key、密码、令牌。

## 考虑过、没有采用

- **输错几次就锁账号**：别人能借此把用户锁在外面，作者也嫌太严。
- **验证码**：现在只给朋友用，先不加；遇到大量自动化尝试再说。

## 什么时候应该重新考虑

- 开放公众注册时（验证码、邮箱验证、两步验证）；
- 日志里看到大量自动化尝试时。

## 怎么验证

`apps/server/test/server.test.ts` 覆盖了这些攻击（2026-11-11）：超长用户名 / 密码、超大请求体、超大 WebSocket 消息、没登录连 WebSocket、别的网站的页面连 WebSocket、连续输错（看等待时间和不锁账号）、一个子应用冒充另一个子应用（D-0090，浏览器里的部分见 D-0090「实测」）。

写测试时发现：WebSocket 连接上的错误（例如消息超过 1 MB）如果不接住，会让整个服务进程崩掉——一条超大消息就能打挂服务器。现在每条连接都接住错误；「超过 1 MB 的消息断开连接，之后新连接照常」的测试会在这个问题回来时失败。以后写网络相关的代码，连接、请求上的 `error` 事件都必须接住。
