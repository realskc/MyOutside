# D-0062 工作流的暂停与恢复由子应用自己解决，平台不提供通用的重放机制

- 状态：有效
- 日期：2026-10-25
- 决策者：作者
- 服务于：
  - 作者预期：[platform.md「平台 AI」](../platform.md)（工作流用代码实现，不受框架性限制）
  - 上游决策：[D-0061](0061-agent-structures-as-platform-base-classes.md)

## 背景

D-0061 之后，需要保存与恢复的状态大多能自然地表达成子应用的数据（消息树、任务图），由平台基类维护——「恢复」就是新建一个指向同一份数据的把手。剩下的是「进度藏在代码执行过程中」的工作流（例如循环进行到第几轮、中间算出来的东西没有写进数据）。

讨论过的通用机制：

- **重放**：工作流与外界的交互都经过 `ctx` 并记日志；中断后从头重跑，已完成的步骤直接取日志结果。要求工作流代码是确定性的；任务暂停期间代码被修改时会对不上；
- **显式检查点 / 状态机**：工作流写成「状态 + 步骤」。

业界的编码 agent 也都只能以「已经完成的步骤」为单位保存：进行中的那一次模型调用被中断就只能丢掉、重来。

## 决策

「进度藏在代码执行过程中」的工作流，其暂停与恢复由子应用在设计时自己想办法解决；平台不提供通用的重放 / 日志机制。

## 影响

- [D-0052](0052-agent-execution-modes.md) 中「后台任务」由平台写日志、重放续跑的设想被本决策取代。

## 什么时候应该重新考虑

- 多个子应用都需要同一种恢复机制，各自实现明显重复时。
