# D-0087 云服务器的基本安全设置：只用密钥登录 SSH，防火墙只开 22，fail2ban，自动装安全更新

- 状态：有效
- 日期：2026-11-11
- 决策者：agent（作者要「简单防御一下黑客攻击，例如把一些端口关了，或者防火墙策略啥的」）
- 服务于：
  - 作者预期：[platform.md「多端」](../platform.md)（作者买了云服务器，第 1 步：看配置和基本能力，简单防御黑客攻击）
  - 红线：[AGENTS.md「红线」](../../AGENTS.md)第 1、3 条（以后作者的生活数据和密钥都会在这台服务器上）

## 背景

服务器开机约 2 小时，就有人在用密码爆破 SSH（一个地址试了约 370 次 root、ubuntu、admin……）。当时 SSH 允许密码登录，`root`、`ubuntu` 都有密码；没有防火墙；没有自动安全更新；有 346 个包待更新，其中 190 个是安全更新。爆破都没成功。

## 决策

- **SSH 只允许密钥登录**，root 不能登录，最多试 4 次（作者的 Mac 会先递一把不对的 RSA 密钥），登录限时 30 秒，关 X11 转发。写在 `sshd_config.d/10-myoutside-hardening.conf`，排在 cloud-init 那份前面。
  - 例外：从 UCloud 控制台所在的内网 10.8.255.0/24 来的连接仍可用密码。作者在控制台的网页登录走这条路（推断），留作后备——Mac 的密钥丢了也能进去。外网到不了这个网段。
- **防火墙**：ufw 默认拒绝进来的连接，只放行 22；部署时再按需放行 80 / 443（2026-11-11 已为 Caddy 放行，见 D-0089）。厂商那层外网防火墙本来就只放行少数端口，两层都要。
- **fail2ban**：SSH 10 分钟失败 5 次封 1 小时，屡犯（一天被封 5 次）封一周。只用密钥后爆破本来就进不来，它主要是挡掉扫描、减少日志噪音。
- **更新**：当场装完所有更新（含新内核）并重启；之后 `unattended-upgrades` 每天自动装安全更新，**不自动重启**。
  - UCloud 改过的 `cloud-init` 不升级（升级会覆盖厂商的改动）。
- **交换空间**：加 4 GB 交换文件（原来没有），避免以后构建、安装依赖时内存不够被系统杀进程。
- **文档里不写服务器的 IP**，用域名 `myoutside.org`（D-0088）：IP 可能会换，以 DNS 为准。

## 考虑过、没有采用

- **改 SSH 端口**：只能减少扫描噪音，不增加实际的安全；还要同时改厂商防火墙、作者要记新端口。只用密钥 + fail2ban 已经够了。
- **ufw 的 `limit`（同一地址 30 秒内连 6 次就拒绝）**：agent 干活时会在短时间里连很多次 SSH，会把自己挡在外面；用 fail2ban 只按失败次数封。
- **完全关掉密码登录（不留控制台的例外）**：更干净，但作者用控制台的网页登录就进不去了，只剩 VNC 方式（没验证过）。
- **自动重启**：内核更新后自动重启会打断正在跑的任务（例如以后哲野在后台逐篇生成）；先手动。

## 代价

- 换一台设备（例如 ThinkBook）登录服务器，要先把它的公钥加进 `authorized_keys`（用 Mac 或控制台）。
- 内核更新要记得手动重启。
- 控制台网段的密码登录还开着，安全性取决于 `ubuntu` 的密码够不够强。

## 什么时候应该重新考虑

- 部署 MyOutside、开放 80 / 443 时（反向代理、TLS）；
- 用上 Docker 时（它会绕过 ufw）；
- 服务器上有了作者的真实数据时：要加备份（快照或异地备份）；
- 多人（同学）开始用时。

## 怎么验证

- 从 Mac：新的密钥登录能连上；强制用密码登录、用 root 登录都被拒（`Permission denied (publickey)`）。
- 在服务器上开着 80 端口的临时网页：服务器内部能访问，从 Mac 访问不到（厂商防火墙放行 80，挡住的是 ufw）。
- 重启两次后：内核是新的，ufw、fail2ban、交换空间、自动更新都还在（第一次重启后 ufw 没起来，见 docs/server.md 的「坑」，已修好）。
