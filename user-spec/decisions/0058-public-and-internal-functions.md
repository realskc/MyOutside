## 背景

前端在窗口里（浏览器环境），后端在 Electron 主进程里（Node 环境），二者之间必然需要一条调用通道。问题是：同一个子应用的前端调后端，是否必须使用与跨应用调用相同的公开 API。

## 决策

- **通道统一**：前端调用自己的后端，也经过内核（与跨应用调用同一条路），享有同样的参数校验、写队列与事务、调用者识别；
- **可见性分级**：后端的每个函数标明
  - **公开**：其他子应用可以调用（还需在自己的清单 `uses` 里声明）；是需要保持稳定的契约；
  - **内部**：只有本子应用的前端（以及本子应用内运行的 agent）可以调用；可以随时修改；
- 推荐多公开：具备完整功能或契约整齐的函数尽量标为公开（作者预期）。
- **前端也可以调用平台与其他子应用的公开 API**：内核按「这个子应用」检查清单 `uses`，前端与后端权限相同。推荐把通用逻辑放在后端；**需要跨子应用原子写入的必须放在后端**——只有后端的写 API 能在同一个事务里调用其他子应用的写 API，前端先后调用两次是两个独立事务。
- 命名：总称 API；公开的叫「公开 API」（跨子应用语境下也可直接叫 API），不公开的叫「内部 API」（`concepts/subapp.md`）。

## 考虑过、没有采用

- **A. 全部是公开 API**：界面专用的小函数也成了公开契约，别人可能依赖它们，改起来束手束脚；agent 的工具列表也会被塞满。
- **C. 前后端走私有通道、绕过内核**：写数据绕过内核会破坏「内核是唯一写入者」、事务与权限检查；多端时每个子应用都要自己处理网络。

## 代价

- 每个函数要多标一个属性。

## 什么时候应该重新考虑

- 可见性的分级方式可以调整（例如更细的分级），但「通道统一经过内核」只有在出现更好的方式保证数据一致与权限检查时才放弃。
