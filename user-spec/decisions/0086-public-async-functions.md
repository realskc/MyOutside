# D-0086 普通的异步函数也可以公开；长事务式的流程，冲突由所有者自己挡

## 背景

网易云下载的「下载」开放不了给纯蓝：它要等网络，又要在下完后记一条下载记录（每天 50 首的额度就是数这个记录，NETEASE-0002）。只读 API 能等但不能写，事务 API 能写但不能等，只有普通的异步函数做得到，而 D-0063 规定它只能是内部 API。作者：这是个好问题，最初的设计会在接下来的使用中慢慢暴露问题（2026-11-11）。

D-0063 当时的理由是让跨子应用的契约保持两种干净的形态（只读，或原子）。作者补充了当时更具体的担心（2026-11-11）：

- 如果每个子应用都把随便什么功能变成公开 API，各路子应用都去调用，就可能发生混乱——指的是**事务层面的写冲突**；
- 这次可以放开，是因为「下载音乐」本身不是一个事务：两个子应用各自发起下载任务，并不会产生冲突；
- 但以后可能有的 API 是一个「长事务」，当作普通的异步函数开放的话会导致冲突，并且是内核难以保证的；
- 现在觉得内核层可能没法保护这一条，还是得子应用自己搞定。

讨论中认可的理由：

- **对被调用的一方没有新难题**：异步函数中途被打断、留下半截，这个问题它本来就得处理——它自己的界面随时可以取消、可以关掉。谁发起的，对它没区别。
- **它碰不到调用方的数据**：内核硬性规定异步函数只能经本应用的事务 API 写数据。别的子应用调用它，只会改它自己的数据。
- **平台自己早就是这种形态**：`platform.ai.chat` 名义上是只读 API，实际要等网络、会花钱、还会写一条用量记录。
- **规矩由所有者自己守**：网易云的排队、间隔、每天上限都在它的后端，谁调用都绕不过，额度共用一份。
- **应用的 API 就是 agent 的工具**：公开后 agent 也能直接用。

## 决策

### 内核

- `defineAsync(schema, handler, { visibility: "public" })`：普通的异步函数可以公开；默认仍是内部。
- 权限照旧：其他子应用要调用，函数必须是公开的，且在自己的清单 `uses` 里声明。
- 谁能调用公开的异步函数：
  - 其他子应用的**前端**、其他子应用的**普通的异步函数**：可以；
  - **只读 API**：不能（会间接写数据，它就不再「只读」）；
  - **事务 API**：不能（事务 API 必须同步）。
- 不变的部分：
  - 写数据只能发生在内核管理的短事务里；异步函数写数据只能经**本应用的**事务 API，**仍不能直接调用其他子应用的事务 API**——要和别人的写入同生共死，只能放在事务 API 里；
  - 事务 API 必须同步、纯数据（D-0007）；
  - 取消信号沿嵌套调用往下传；子调用的进度事件原样推给最初发起调用的界面（与 `platform.ai.chat` 的流式相同）。

### 「长事务」不能随便当作公开的异步函数：冲突由所有者自己挡

- **内核保证到短事务为止**：每次事务 API 调用原子、写入排成一条队（D-0004）；一个普通的异步函数是一串各自独立的短事务，内核**不保证整体**。
- **可以放心公开的**：本身不是事务的流程。例：下载音乐——几个子应用各自发起下载，互不冲突（同一首歌的重复也由网易云的排队和「不覆盖」挡住）。
- **要小心的是「长事务」**：中间读到的东西，在等外部的期间不能被别人改，否则结果就错。例：学英语的「判重 → 加卡片」——两处同时加同一个词，都判断「没有重复」，就会加出两张。拆成异步函数后，几个调用方的步骤会互相穿插，产生事务层面的写冲突，内核难以保证（作者）。
- 作者的原则：不是公开 API 时，防并发是子应用内部的问题，可以在调用层面解决（例如界面上把按钮变灰）；一旦作为公开 API 发布，**不管别人怎么调**（同时调用、反复调用、顺序奇怪、调到一半取消），API 都必须能防住。所以公开之前，**所有者必须在 API 里面挡住冲突**——做在检查和修改共享状态的地方，不能靠界面；挡不住就不公开。「挡住」不一定是不许并发，而是不管怎么穿插，要守的条件都成立。做法任选，契约里写明用的是哪种：
  - 事务 API 里的提交时校验（D-0063；例：VOCAB-0010 加卡片时带上判断时看到的卡片 id，多出卡片就 `CONFLICT`）；
  - 在应用内部排队，一次只做一个（例：网易云的下载，NETEASE-0002）；
  - 直接拒绝并发（例：纯蓝的「这首曲目正在分离」）。
- 这条不只管异步函数：公开的事务 API、只读 API 单独看天然安全（事务原子，只读不写），但如果设计的用法是「先调我的只读 API 看一眼，再调我的事务 API 去改」，这一对在调用方那边就是一个长事务，事务 API 要把调用方看到的东西当前提收进来、提交时核对。例：加生词要先调 `vocab.resolveCard` 判重（问 AI，要几秒；在学英语界面里还要等作者选），再调 `vocab.addCard`。这中间别处可能刚加了同一个词，按旧的判断去加就会重复；所以 `addCard` 收下判重时看到的卡片列表（`knownCardIds`），提交时发现这个词多出了卡片，就报 `CONFLICT`、让调用方重新判断（VOCAB-0010）。
- 反例（现在没问题，公开前要改）：纯蓝的 `startSeparation` 先查「有没有正在分离的任务」，再用另一个事务插入任务，插入时不再查。现在只有纯蓝自己的界面调用、分离时按钮变灰，靠调用层面挡住了；要公开，就得把检查挪进插入任务的事务里。
- 内核的职能（作者认可）：把出问题的范围锁在一个子应用里——再怎么乱，乱的只是被调用的子应用自己的数据。内核要不要再提供锁、版本号这类工具，作者：再说吧（2026-11-11）。

### 公开的异步函数，契约要多写几样

写在 `packages/contracts` 对应的注释里（软约束，内核不检查）：

- **进度事件的格式**：事件会原样推给发起方的界面，所以也是契约的一部分；
- **中途失败或取消后，本应用这边留下什么**（例：下载取消后不留音频文件、不记下载记录）；
- **会不会排队、大概要多久**；
- **被同时调用多次时怎么样**（排队、拒绝，还是提交时校验失败报 `CONFLICT`）；
- **调用方要等它结束（或取消），不能「发起后不管」**：宿主只跟踪最外层的调用；外层函数先返回的话，没等完的子调用既没法再取消，退出 MyOutside 时也不会收到取消信号。

### 第一个使用者

`netease.download` 改为公开（作者：最多向纯蓝开放「下载」和「访问下载的音乐文件夹」）；搜索仍是内部 API。

## 考虑过、没有采用

- **平台「长任务」**（发起后马上返回任务 id，之后查进度、取消；外壳统一显示后台在做的事）：它解决的是「调用方不用一直挂着、换页面后还能接回来」。但现在切走面板，调用照样在后台跑完；要接回来，应用把进度记进自己的数据即可（纯蓝的分离就是这样，66CCFF-0006）。代价是平台多一个概念、几张表，还要管结果保留、谁能取消谁的任务、重启后怎么标记中断，与 D-0062「平台不做通用的暂停与恢复」也有冲突。
- **投递请求**（调用方用公开事务 API 往对方的待办表里塞一条，对方后台自己处理，调用方之后再查）：内核不用改，能跨重启，也能和调用方的写入一起原子提交；但依赖「启动时的后台工作」（D-0076，未实现），调用方只能轮询结果，每个想这样做的应用都要自己写一套。适合「整张歌单慢慢下」这类需求，那是所有者自己的功能，不需要平台改。
- **把下载改成只读 API 绕过规则**：记不了下载记录，每天的额度就数不准。
- **外层函数返回时，内核自动取消它没等完的子调用**（把「必须等它结束」变成硬约束）：现有代码里有「发出去不等」的进度写入（例如纯蓝的 `updateJob`），一刀切会误伤；先作为契约里的软约束。
- **异步函数可以直接调用其他子应用的公开事务 API**：前端已经可以这样做，但后端没有这个需求；放开会让「跨子应用的写入」多一条不原子的路，先不放。

## 代价

- 跨子应用的契约多了一种形态：不原子、可能很久、会推进度事件；调用方要读契约才知道失败或取消后对方留下了什么。
- 长事务式的流程会不会冲突，靠所有者自觉；内核只保证每个短事务原子、写入不越界。这和 platform.md「结构上不会出现写冲突，不依赖开发者自觉」之间有缺口——D-0063 起内部的异步函数就有这个缺口（platform.md：现行方案暂时可行，以后可能引入锁机制），公开以后调用方更多，更容易碰到。
- 子调用的事件与发起方自己的事件混在同一个推送通道里，界面要自己分辨。

## 什么时候应该重新考虑

- 出现一个要公开的长事务、所有者自己挡不住冲突时（考虑由内核提供长事务机制，例如逻辑锁、乐观的版本检查——D-0063 里暂缓的那条）；
- 多个子应用都在重复写「任务记录 + 重新打开后接回来」，或者想在外壳里统一看后台任务时（考虑平台长任务）；
- 出现调用方「发起后不管」造成的问题时（考虑把「必须等它结束」变成硬约束）；
- 子调用的事件和发起方的事件混在一起、界面分辨不清时（考虑让 `ctx.call` 带一个选项，由调用方接住子调用的事件）；
- 安装别人写的子应用、要评估信任边界时。
