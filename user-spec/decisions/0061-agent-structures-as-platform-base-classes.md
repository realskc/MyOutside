# D-0061 通用 agent 结构以平台基类提供，数据存在子应用自己的表空间

- 状态：有效（未实现）
- 日期：2026-10-25
- 决策者：讨论
- 服务于：
  - 作者预期：[platform.md「平台 AI」](../platform.md)（通用的 agent 结构由平台支持；agent 框架必须共享）
  - 作者预期：[platform.md「数据归属与子应用之间的连接」](../platform.md)（每份数据有唯一所有者；子应用之间不得混乱地相互调用）
  - 作者预期：[platform.md「子应用的形态」](../platform.md)（agent 状态的维护与存储都在后端）

## 背景

讨论「持久任务怎么设计」时，作者区分出几个层次（从大到小）：

| 层次 | 例子 |
|---|---|
| 子应用 | 对话应用、哲野 |
| 大型 agent 状态：结构化的消息 / 工作数据 + 当前进行到哪 | 对话的一个会话（消息树 + 当前叶节点）；哲野的一次讲解（单元与前置的依赖图 + 生成进度） |
| 小型 LLM 流程 | 生成一次回复（工具循环）；判重 |
| LLM API | 单次调用 |

讨论中形成的认识：

- **层次是相对的**：例如哲野「生成一篇文章」本身也可以是一个大型状态，里面嵌着更小的流程。
- **整个子应用不是一个工作流**：对话应用里只有「生成回复」是工作流；切换分支、重命名等是普通的数据操作。消息树是子应用的数据，工作流把当前路径当作输入、把结果写回。
- **哪些东西需要保存和恢复**，判断标准是「中断时丢掉它，用户会不会损失在意的东西」（看得见的进度、重做代价高、在等外部、已产生不该重复的效果）。按此判断：学英语复习不需要；对话回复丢了可重试，但不应因切换子应用而丢；哲野一篇文章需要；哲野一整次讲解必须。
- **作者希望平台支持大型 agent 状态这一层的出发点是通用性**：对话的消息树、哲野式的任务图都是很通用的 agent 结构，与具体子应用无关；也希望 agent 能力能被更独立地讨论与设计。后者确实是动机，但作者认为它不一定有道理：一是这个动机本身不一定有意义——暂时无法衡量利弊，不知道未来的需求与情况；二是为了这个动机去专门把 agent 能力模块抽象出来，也不一定有意义。整体上与「重放 / 恢复」的实现机制关系不大。
- **两种通用结构**：消息树（分支互相替代，同一时刻只选中一条；操作是追加、分叉、切换、取路径）与任务图（子节点都要完成；操作是找出可开始的工作、标记完成、等人回答）。存储层面可以统一成「节点 + 连线 + 状态」，语义层面难以统一；二者可以互相包含（任务图的节点里挂一棵消息树；消息树的一步里发起一张任务图）。作者没想明白是否存在更好的统一设计，现阶段当作两种东西。

## 决策

- 平台以**可继承的基类**提供通用 agent 结构：消息树、任务图。**存储逻辑写在基类里**，表结构也由类声明；
- 子应用**继承基类做定制**：声明额外的字段（随建表或迁移生成列）、覆盖行为（例如怎样把消息路径转成发给模型的消息）。作者的要求只是「子应用在平台提供的能力上改造」，继承只是一个粗糙的想法，没有要求具体形式（继承、钩子等都可以）；
- **数据存在子应用自己的表空间**（例如哲野的批注线程存在 `zheye__…`），归子应用所有；
- **类对象是指向数据的把手**（作者预期，见 `platform.md`）：对象持有子应用借给它的数据库句柄与表名，在子应用的事务里直接读写；对象本身不保存数据，「当前进行到哪」也存在表里；每次调用时新建、用完即丢；
- **建表放在子应用的迁移里**：基类提供根据声明的字段生成迁移的辅助；写数据（追加、分叉等）由基类直接通过句柄完成。没有采用「基类只算出要写什么、由子应用自己写」：每个子应用都要重复写入逻辑，漏一步（例如忘了更新分支指针）数据就会坏；
- 其他子应用需要使用时，通过**拥有者的公开 API**；
- 存储方式不变：仍是 SQLite 的表。

## 考虑过、没有采用

| 方案 | 做法 | 没有采用的原因 |
|---|---|---|
| **甲：平台托管大型 agent 状态** | 子应用定义状态类，平台负责保存、恢复、驱动（类似 Cloudflare Durable Objects、Orleans 的「有状态对象 / 虚拟 actor」） | 大型 agent 状态往往就是子应用最核心的数据（消息树就是对话的主要数据），子应用还要基于它做会话列表、用量统计、搜索等查询；有状态对象通常把状态存成一整块，跨实例查询弱；各子应用的状态形状差异很大（树、依赖图、计划、文件）；平台保存的通用状态还需要一套新的迁移机制 |
| **乙：平台不管这一层** | 大型 agent 状态完全由子应用自己存，平台只支持小型 LLM 流程 | 每个子应用都要重复实现消息树、任务图，违背「agent 框架必须共享」 |
| **B：平台服务，数据由平台保管** | 平台提供「线程」等平台 API，所有子应用的数据存在平台的表里、标明归属；线程是平台上可被引用的公共对象 | 作者指出：跨子应用使用本来就应该通过包装良好的公开 API，而不是让一个子应用直接访问另一个子应用的数据。B 的「公共对象、谁都能直接读写」反而与「每份数据有唯一所有者、子应用之间不得混乱地相互调用」冲突 |
| 共享代码模块但不可继承 | 平台提供固定的模块与表结构 | 子应用无法定制字段与行为；改为可继承的基类即可 |

讨论中的两点修正：

- 最初认为「A（共享代码）便于加自定义字段，B 不便」——实际上两者都可以用「预留扩展字段」或「旁挂一张自己的表、用节点 ID 对应」来扩展，差别不大；A 剩下的实际优势是：旁挂表与基类的表在同一个表空间，可以直接联表查询。
- 最初认为 A 的短板是「跨子应用共用同一条线程不方便」——作者指出这不是短板：跨子应用本来就应走拥有者的公开 API。

存储方式也讨论过其他选择（JSON / 文档、键值、文件、只追加的事件日志、图数据库、向量索引、全文索引、CRDT），作者决定存储保持不变。理由：现在没法考虑利弊——不知道未来真实的数据需求（要存什么、哪些东西会频繁修改、是否真的会有迁移之类的需求）。其中多数可以「住」在 SQLite 里（JSON 列、全文索引、向量扩展、事件日志表），内核的事务与数据归属保证仍然有效；将来基类内部可以考虑用只追加的方式存消息树，以获得「回到任意历史状态」的能力。

## 代价

- **加字段仍需迁移**：表已存在时再加字段要走迁移；基类需要配套提供「根据声明的字段生成迁移」的辅助；
- **脆弱基类**：平台改动基类（新增基础字段、改变方法行为）会影响所有子类，可能需要各子应用分别迁移，也可能意外改坏子类；基类的扩展点要克制，改动时保持兼容；
- 各子应用的数据是各自的副本，平台改进基类后，每个子应用的表都要迁移一遍。

## 不在本决策范围内

- 持久任务的暂停与恢复机制（重放、由业务数据推出下一步、显式状态机等），另行讨论；
- 子应用在基类上改造的具体形式（继承、钩子等），实现时选。

## 什么时候应该重新考虑

- 找到了能把消息树与任务图统一起来的更好设计；
- 基类的定制方式不够用，或脆弱基类问题变得严重；
- 出现大量需要跨子应用共享、且不适合通过公开 API 包装的 agent 结构。
