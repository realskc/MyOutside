# D-0001 一次性需求以「临时函数」完成：软门槛、自动留痕、无晋升

- 状态：有效
- 日期：2026-10-01
- 决策者：用户
- 服务于：
  - 用户预期：[principles.md「需求观：一次性需求是合理的」](../principles.md)
  - 用户预期：[principles.md「约束：软约束与硬约束都要」](../principles.md)

## 背景

一次性需求（批量导入既有数据、手工修正某个自动计算的字段……）是合理的，但现有接口往往表达不了。需要一种形态，让 Agent 能在接口之外完成这件事，同时保证用户知情、事后可追溯、不会悄悄变成永久功能。

## 决策

标准形态是**临时函数**：一段一次性代码，限定作用域、执行一次、自动留痕、立即消失。三个配套机制：

1. **软门槛**：发起前向用户说明并获得确认；确认内容包含**作用域**——这次只允许直写哪几个应用的数据（作用域外一律走对方的 API）。
2. **自动留痕**：意图、完整源码、参数、作用域、影响与结果由内核自动写进日志（自然语言即可）。
3. **无晋升**：临时函数不可永久保留，执行一次后立即注销（无论成败）。要永久化，只能由 builder 显式发起「永久修改」并经用户同意。

另外，临时函数仍**经内核执行**（串行队列 + 事务）；内核未运行时不允许直接改库。

## 考虑过、没有采用

- 用固定接口抵御临时需求（要么提供通用接口，要么拒绝）：上一个时代的做法，与「一次性需求是合理的」相悖。
- 临时函数可以晋升为永久函数：会让一次性代码悄悄沉淀成未经设计的永久功能。

## 代价

- 临时函数运行在内核进程里，理论上具备 Node 的全部能力；控制手段是软门槛 + 源码留痕 + 用户过目，不是硬隔离。

## 什么时候应该重新考虑

- 使用者不再是作者本人（阶段 1 之后），需要更硬的隔离时——可考虑受限子进程执行。
