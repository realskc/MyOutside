# D-0081 所有应用的物理表名统一加 `app_` 前缀

- 状态：有效
- 日期：2026-11-06
- 决策者：作者
- 服务于：
  - 作者预期：应用标识与命名（PB-0005）
  - 上游决策：[D-0053](0053-kernel-enforced-call-permissions.md)（清单声明、内核检查）

## 背景

内核原先直接把 `<appId>__<table>` 当物理表名，因此应用 id 必须满足 SQL 标识符规则（字母或下划线开头）。这会让 `66CCFF` 这类数字开头的名字无法作为 id。

当前仍是早期开发阶段，应用少、数据迁移成本低。作者希望统一规则，而不是为单个应用做特例。

## 决策

- 所有子应用的物理表名统一为 `app_<appId>__<table>`；逻辑表名仍由应用使用 `track`、`card` 等短名；
- 应用 id 允许数字开头，但仍限制在 `^[A-Za-z0-9][A-Za-z0-9_]*$`，以便物理表名、索引名和调用名安全；
- 应用 id 用于显示、API 前缀和数据目录时保留原始大小写；URL host / npm 包名按规范使用小写；
- 已有数据库一次性迁移：应用表、显式索引名、`platform_migration.app_id`、`platform_usage.caller`、`sqlite_sequence`；应用数据目录同步改名；
- 新安装从 `app_` 前缀开始，不再产生旧格式表名。

## 考虑过、没有采用

- **只给 `66CCFF` 加特殊前缀**：规则不统一，后续每遇到数字开头或 SQL 关键字都要再特判。
- **所有 SQL 标识符加引号**：可以做到，但改动面大、容易漏；固定前缀更简单可靠。
- **让应用 id 继续受字母开头限制，只改显示名**：作者明确要求内部也不保留旧 id，不能接受。

## 代价

- 现有本地数据库和应用数据目录需要迁移一次；
- 表名变长，调试时看到的是 `app_66CCFF__track` 而不是 `66CCFF__track`；
- 应用 id 的大小写与 URL / npm 包名的小写形式需要做映射。

## 什么时候应该重新考虑

- 应用 id 需要支持连字符等更多字符 → 需要更完整的 SQL 标识符编码规则；
- 需要给第三方应用提供兼容旧表名的插件机制；
- 数据库抽象层更换，标识符规则不再由 SQL 决定。
