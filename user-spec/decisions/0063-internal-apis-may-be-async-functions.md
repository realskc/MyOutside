# D-0063 写数据只能通过事务 API；公开 API 只能是只读或事务，内部 API 还可以是普通的异步函数

## 背景

讨论工具循环的每一步如何保存时，发现一个问题：要「等模型回复 → 保存这一步 → 再等 → 再保存」，现有规则下没有任何一种 API 能做到——只读 API 能等，但不能写、也不能调用事务 API；事务 API 能写，但必须同步、几毫秒完成。唯一的办法是让前端来回调度，违背「agent 状态在后端维护」。学英语的「先判重、再加卡片」（D-0008）也是同样的困境。

作者指出两点：

- 事务 API 设计上就是原子、快速的修改操作，不是用来解决这种问题的；
- 追问：最初为什么要求 API 必须要么只读、要么事务？

回顾 D-0007，这条要求的目的可以归结为一条真正的规则：**写数据只能发生在内核管理的短事务里**（进写队列、原子、不会长时间挡住其他写入、不会有不在事务里的写入、事务 API 之间可以组成跨子应用的原子写入）。「API 要么只读、要么事务」只是当时落实这条规则最简单的办法——那时多步操作都由前端串起来，后端不需要「边等边写」的代码。

## 决策

- **真正的规则**：写数据只能发生在内核管理的短事务里，即只能通过事务 API；
- **公开 API**：只能是只读 API 或事务 API——跨子应用的契约保持两种干净的形态（只读，或原子）；
- **内部 API**：除了只读 API 与事务 API，还可以是**普通的异步函数**：
  - 可以等外部（模型、搜索等）；
  - 写数据只能通过调用本子应用的事务 API，每次调用是一个独立的短事务；
  - 整体不保证原子，可能在两个短事务之间被打断——这种复杂性留在子应用内部；
  - 不另起名字：就叫内部 API，需要区分时说「普通的异步函数」；
- **步骤之间的一致性**（例如生成期间对话路径被修改）由子应用在事务 API 里做**提交时校验**：事务 API 里的「读 → 检查 → 写」是原子的，检查可靠；发现冲突就拒绝写入，异步函数随之停止。

示例（示意）：

```ts
// 对话后端：内部 API，普通的异步函数
continueReply(ctx, threadId):
  循环：读出当前路径 → 已回答完则结束 → 推进一轮（等模型、执行工具）
        → 调用事务 API saveStep(threadId, expectedLeafId, step)

// 对话后端：事务 API
saveStep: 若当前末端 ≠ expectedLeafId → 报冲突、回滚；否则把这一步存成节点
```

## 考虑过、没有采用

- **新增一种公开的「编排 API」**：可以被其他子应用调用的非原子 API 会让跨子应用的契约变复杂；限定在内部即可。
- **放宽只读 API，允许它调用事务 API**：它就不再「只读」，名字与定义都要改，概念变混乱。
- **普通函数可以直接写数据库**：绕过写队列与事务，崩溃时会留下写了一半的数据，破坏真正的规则。
- **继续由前端调度**：违背「agent 状态在后端维护」；切换子应用或关闭时流程会断。
- **由内核提供长事务机制（逻辑锁、草稿隔离等）**：现阶段不需要；子应用层面用「异步函数 + 事务 API 里的提交时校验」即可，且没有引入长事务。将来需求清楚了再考虑。

## 什么时候应该重新考虑

- 多个子应用都在重复写同样的提交时校验逻辑，或校验不足以保证一致性时（考虑由内核提供逻辑锁、草稿隔离等机制）。
