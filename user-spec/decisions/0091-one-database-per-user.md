# D-0091 多用户：每个用户一个独立的数据库，服务器为每个用户各开一份内核

- 状态：有效（未实现）
- 日期：2026-11-11
- 决策者：agent 提议；作者给了检验标准（「假如哪天有了 10000 个用户，这样的方式是否会带来过大的代价？不会就行，会就不行」），agent 按这个标准分析后采用
- 服务于：
  - 作者预期：[platform.md「多端」](../platform.md)（用户注册登录，不同用户的数据独立）、[platform.md「分发与隔离」](../platform.md)（用户不能影响其他用户）、[platform.md「平台 AI」](../platform.md)（每个用户用自己的 API key）
  - 上游决策：[D-0004](0004-sqlite-single-writer-queue.md)（SQLite 单写者队列）、[D-0013](0013-cloud-kernel-for-multi-device.md)（云端内核）

## 决策

- 服务器上每个用户一个 SQLite 数据库文件；每个用户各有一份内核实例（自己的写队列、迁移记录、平台设置——包括他自己的 API key、用量记录）。
- 子应用的代码不用知道「有多个用户」：它拿到的 `ctx.db` 就是当前用户的库。
- 只给正在用的用户打开内核和数据库连接，闲置一段时间后关掉。
- 表结构迁移在用户的内核打开时跑（和现在内核启动时跑迁移一样）。

## 按「1 万个用户」检验

| 方面 | 1 万个用户时 |
|---|---|
| 磁盘 | 空库约 0.2 MB（2026-11-11 实测作者的库：托福词表等种子数据只占约 0.14 MB；作者的 11.7 MB 里 11 MB 是哲野的试跑日志），1 万人的空库约 2 GB；用户自己的数据放在一个库里也是这么多 |
| 内存 | 不会 1 万人同时在线；只开正在用的人的内核 |
| 写入 | 一人一条写队列，互不影响；所有人一个库的话，1 万人的写入排同一条队，反而是瓶颈 |
| 扩容 | 一台服务器不够时，把一部分用户的库文件搬到另一台 |
| 迁移 | 每个库各跑一遍，在打开时跑；失败只影响那一个用户，要有办法发现 |
| 备份 | 1 万个文件，用只传变化部分的增量备份 |

结论：代价不大。每个用户 / 每个租户一个 SQLite 也是业界常见的做法（例如 Cloudflare Durable Objects 每个对象带一个 SQLite；Turso 主打「每个用户一个数据库」，agent 的印象，没逐条核对）。

## 考虑过、没有采用

- **所有人一个库、每行标上属于谁**：每个子应用的每条查询都要记得按用户过滤，漏一处就泄露别人的数据；所有人的写入排同一条队；子应用代码要全改。

## 代价

- **跨用户的事变难**：两个人一起下围棋、统计「多少人在用某个子应用」，都要专门设计，不能一条查询搞定。
- 种子数据（如托福词表）每个用户各有一份；量小，先不管。
- 改表结构要更小心：迁移要在很多个库上各成功一次。

## 什么时候应该重新考虑

- 出现大量跨用户的功能时；
- 用户数远超 1 万、或单个用户的数据大到 SQLite 吃力时。
