# D-0090 浏览器里，子应用的界面放进沙箱 iframe；外壳按「消息来自哪个 iframe」认出调用者

- 决策者：agent 提议，作者同意（作者：iframe 相关不太懂，暂且听 agent 的）
- 服务于：

  - 上游决策：[D-0018](0018-iframe-panel-and-app-protocol.md)（外壳里一个 iframe 作面板）、[D-0053](0053-kernel-enforced-call-permissions.md)（内核按调用者检查权限）、[D-0013](0013-cloud-kernel-for-multi-device.md)（云端内核）

## 背景

部署到服务器后，子应用的界面要能在普通浏览器里用。内核按调用者检查权限（清单 `uses`），前提是认得出「这次调用是哪个子应用发的」，而且子应用伪造不了。

- 在 Electron 里，主进程按发起调用的页面地址（`app://<id>/`）认人，页面伪造不了。
- 在浏览器里，如果所有子应用的界面都放在同一个源（同一个域名）下，它们能互相读对方的页面、cookie、本地存储，任何一个子应用都能冒充别的子应用调用。局域网预览就有这个问题（D-0072：按 Referer 认人，可以伪造）。
- 子应用各自持有凭证也不行：同一个源下，凭证能被别的子应用读走（作者指出）。
- 每个子应用一个固定的子域名也不行：每个用户的子应用可以不一样、名字随意（作者），只能当临时过渡。

## 决策

- **子应用的界面放进沙箱 iframe**：外壳给子应用的 iframe 加 `sandbox`（只允许运行脚本等必要的项，不给 `allow-same-origin`）；服务器返回子应用的页面时也带上 `Content-Security-Policy: sandbox …`，这样就算直接打开子应用的网址，它也照样被关在沙箱里。被关起来的页面，浏览器给它一个独一无二的「无名源」（opaque origin）：读不到外壳和其他子应用的页面、cookie、本地存储，也不能直接带着用户的登录状态请求服务器。
- **调用经外壳转交**：子应用的 `window.outside.call` 用 `postMessage` 把请求交给外壳；外壳按消息的 `event.source` 是自己建的哪个 iframe 认出调用者（浏览器填的，子应用伪造不了；不是外壳直接建的 iframe 发来的消息一律拒绝），再带上用户的登录状态转给服务器。进度事件、取消也经外壳转。这和现在 Electron 由主进程按页面认人是同一个思路。
- **子应用的地址随意**：都在 `myoutside.org` 下，按路径区分，不需要额外的子域名和证书。
- 外壳是平台自己的代码，是这套隔离的关键，要写严。
- 实现前先在 Chrome、Safari、Firefox 里实测上面这些浏览器行为（无名源读不到别人的存储、CSP 的 `sandbox` 对直接打开也生效、`event.source` 能区分 iframe）。
- **每次打开子应用都新建一个 iframe**，换掉旧的：旧页面在卸载前发来的消息，`source` 对不上任何现有的面板，不会被算到新打开的子应用头上。
- **子应用的本地存储** `outside.storage`（`get` / `set` / `remove`，值是字符串）：外壳按子应用分开，存在自己的 localStorage 里（键是 `mo.app.<应用 id>.<键>`），只在这台浏览器上。

## 考虑过、没有采用

- **同一个源下，按路径或 Referer 认人**：可以伪造（D-0072 的问题）。
- **每个子应用持有凭证**：同一个源下凭证会被别的子应用读走。
- **每个子应用一个子域名 + 通配证书 `*.myoutside.org`**：隔离也够，子域名可以用平台分配的编号（不用应用名），一张证书就够；但服务器上要放一个能改 DNS 的 Cloudflare 令牌（申请通配证书要 DNS 验证），还要防兄弟子域名往主域名上塞 cookie。将来某个子应用确实需要一个真正的源时，可以再用它。

## 代价

- 子应用不能用浏览器自己的存储（localStorage、cookie、IndexedDB），要存东西就存进自己的后端或平台提供的存储。现在只有围棋用 localStorage 存座位令牌，有了登录以后改成按用户认座位。
- 少数浏览器功能用不了，或者要外壳代办：离线缓存（Service Worker）、麦克风 / 摄像头 / 通知这类要申请的权限等。纯蓝在 Web Audio 里分析音频，要给音频加跨源的响应头（纯蓝这一步留在本地，暂时碰不到）。
- 所有调用多经过外壳一跳（同一个页面里的消息传递，开销很小）。

## 什么时候应该重新考虑

- 某个子应用必须要一个真正的源（例如离线使用、长期的麦克风权限）时：考虑给它单独的子域名；
- 浏览器实测发现上面的行为不成立时；
- 这只管界面这一半；子应用的后端也要关起来，才能防住恶意子应用（见 platform.md「分发与隔离」的 agent 注），那是另一条决策。

## 实测（2026-11-11，Chromium：Electron 38 自带的；`apps/server/scripts/browser-check.cjs`）

- 子应用页面的源是 `null`；读外壳的页面、localStorage、cookie 都被挡住；直接 `fetch` 服务器、直接连 WebSocket 都失败（服务端按 Origin 拒绝）；
- 子应用冒充外壳改平台设置：`FORBIDDEN`；
- 子应用页面里再嵌一个页面，从里面直接给外壳发调用、或用它自己的桥调用：外壳都不理；
- 切换子应用：换成了新的 iframe 元素，旧的已移出页面；
- 对话的调用正常、KaTeX 字体能加载；围棋的座位令牌重新打开后不变。
- Safari、Firefox 还没测。
