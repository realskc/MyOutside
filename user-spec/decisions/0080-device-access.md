# D-0080 设备上的数据是普通文件夹；子应用访问设备要在清单里登记，经内核与设备之间的通道

- 状态：有效（未实现）
- 日期：2026-11-05
- 决策者：作者
- 服务于：
  - 作者预期：[platform.md「多端」](../platform.md)（设备）
  - 上游决策：[D-0013](0013-cloud-kernel-for-multi-device.md)（云端内核）、[D-0053](0053-kernel-enforced-call-permissions.md)（清单声明、内核检查）

## 决策

- 需要大量本地数据的工作（例如科研），数据就放在用户电脑上的**普通文件夹**里：MyOutside 和电脑上的其他程序（git、PyTorch……）都可以正常访问，MyOutside 不额外限制它的访问边界。
- 子应用要访问设备（读写设备上的文件、运行设备上的程序），需要**在清单里登记**，由内核检查。
- 内核与设备之间要有**通道**：将来内核在云端（D-0013），设备是另一台机器。

## 考虑过、没有采用

- **项目「在 MyOutside 里」，受 MyOutside 管理**（作者提出，后来放弃）：科研文件夹不必是电脑上的普通存在；只有特定的子应用能访问，电脑上的外部软件一般都要通过 MyOutside 访问（边界量力而为）。它消除了「必须是普通目录」的限制。讨论过的做法：外部程序由 MyOutside 开「会话」启动；防止外部软件绕过 MyOutside 的三档做法（藏起来并监视改动、平时存成加密磁盘镜像、按进程放行的虚拟文件系统）。放弃的原因：作者想了想，没有那么强的需求去限制这个边界。
- **让子应用受限地访问电脑上的任意目录**（按文件夹授权、套沙箱）：技术上和沙盒本质一样，本质困难（作者）。

## 什么时候应该重新考虑

- 需要限制外部程序或子应用碰某些本地数据时，例如开始安装别人写的子应用以后（正式阶段）；
- 开始实现云端内核时：细化通道与授权。

## 现状

- 现在内核和设备是同一台电脑（都在 Electron 里），通道还不存在；子应用的后端在内核进程里，技术上能直接读写本机文件，清单登记目前约束不到这一点。
