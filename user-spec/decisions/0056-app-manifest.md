# D-0056 应用清单（manifest）的内容与形式：每个子应用一份 JSON 文件

- 状态：有效（未实现）
- 日期：2026-10-23
- 决策者：agent（「要有清单、清单在 builder 上有独立的权限限制」是作者的预期；内容与形式是 agent 的方案）
- 服务于：
  - 作者预期：[platform.md「子应用的形态」](../platform.md)（每个子应用有一份清单，将来在 builder 上有独立的权限限制）
  - 作者预期：[principles.md「统一的内核让 agent 更安全」](../principles.md)
  - 作者预期：[principles.md「耦合哲学」](../principles.md)（子应用创建、删除、修改成本低）

## 背景

描述子应用的信息（id、名称、API、迁移、`owns`）目前写在后端代码的 `AppModule` 对象里；原协议设想的清单字段（前端 / 后端入口、协议版本）没有实现，Electron 主进程代码里硬编码了每个应用的导入、注册与界面目录；`owns` 写了但内核不读。

## 决策

**形式**：每个子应用一份独立的 JSON 文件（例如 `apps/dialog/manifest.json`），与代码分开存放。

**内容**：

- 描述性字段：`id`、`name`、`protocolVersion`、前端入口、后端入口、`owns`——平台据此自动发现与装载应用，新增应用不再需要修改 Electron 主进程代码；
- 权限字段：`uses`（会调用哪些其他应用 / 平台的函数，D-0053）——内核据此做硬检查。

API 函数与迁移仍由后端代码提供（它们本来就是代码）。

**谁能修改**：开发阶段 agent 可以随意修改；builder 修改清单的权限另行讨论（`future/builder.md`「未定」）。

## 理由

与代码分开存放，才可能对清单单独施加权限限制（改代码不等于改权限）。用 JSON 文件是最简单的形式。

## 考虑过、没有采用

- 写在 `AppModule` 代码里：谁能改代码就能改权限。

## 什么时候应该重新考虑

随时可以——例如改为存进数据库、由内核管理（将来做 builder 的批准流程时可能更合适）。只要仍满足「清单与代码分开、能被单独施加权限限制」。
