# 平台

## 技术选型的总体预期

- 开发以 AI Agent 为主，技术选型与架构**优先考虑 Agent 的可迭代性**（见 [D-0003](decisions/0003-single-language-typescript.md)）。
- MyOutside 是在 Windows、macOS、Linux 上表现一致的桌面应用（平台要求见 `product.md`；Electron 实现见 [D-0002](decisions/0002-electron-host.md)）。

## 子应用的形态

- 每个子应用由两部分组成（概念见 `concepts/subapp.md`）：
  - **后端**：拥有自己的数据，对外提供功能；**没有前端也能被调用**（例如被其他子应用调用）；
  - **前端**：只通过**自己的后端**访问数据。
- 分工：后端负责数据，以及不管谁来调用都必须成立的规则；前端负责显示与交互流程。
- **工作流的状态，维护与存储都在后端**，前端只负责读取（以及发起操作）。例：对话回复生成完毕后由后端直接保存，不依赖前端是否还在。
- 前端可以调用平台和其他子应用的公开 API（同样受清单约束）——前端与后端同属一个子应用，权限相同；只是**更推荐让后端实现通用逻辑**，方便其他子应用与 agent 复用。
- 子应用**安装即常驻**，没有启用 / 停用的概念（这是预期，但理由还没完全想清楚，见「未定」）。
- **每个用户的子应用可以不一样，子应用想怎么命名就怎么命名**（作者，2026-11-11：讨论部署时提出；所以平台不能靠「每个子应用一个固定的子域名」这类办法区分子应用，那只能当临时过渡）。
- 每个子应用有一份**清单（manifest）**：描述这个应用，并声明它的权限。清单将来在 builder 上有**独立的权限限制**——不能随着改代码一起被随意修改（具体规则另行讨论，见 `future/builder.md`）。清单以什么形式存在是实现方案（见 [D-0056](decisions/0056-app-manifest.md)）。

## 数据归属与子应用之间的连接

子应用之间要能耦合（见 `principles.md`「耦合哲学」），而且**耦合的子应用要容易连接、也容易剥离**。为此有两条非常重要的预期：

1. **每一份数据都必须有一个唯一确定的所有者**（某个子应用，或平台本身）。
2. **子应用之间不得用任意方式混乱地相互调用**：跨应用的读写与调用，都要经过明确的通道。

数据以什么形式存储（例如是不是「表」）、通道具体长什么样，都是实现方案（当前见 [D-0005](decisions/0005-data-ownership-by-table-prefix.md)、[D-0006](decisions/0006-cross-app-calls-via-owner-api.md)、[D-0058](decisions/0058-public-and-internal-functions.md)）。

**推荐子应用多公开功能**：具备完整功能、或契约整齐的功能，尽量对外公开，为其他子应用提供便利。外部子应用用不用是另一回事——要用的话，也需要在清单里声明。

## 分发与隔离

- **分发形态**（作者，2026-11-11，作者理想中的）：用户可以通过浏览器登录、使用子应用（甚至别人写的子应用）；也可以通过本地 app 使用 MyOutside。
  - 本地 app 理论上是连到服务器的桌面客户端：数据在服务器上，本地 app 相当于浏览器再加上设备能力（作者，2026-11-11）。不过多设备还没讨论，网易云下载这类的应当有其他考虑（作者）。
- **现阶段不开放公众注册，只给朋友用用**（作者，2026-11-11）。
- **一定要防黑客**（作者，2026-11-11）：例如用两百万位长的用户名尝试登录这种攻击。哪怕服务器上还只是测试数据，作者的 API key 也在上面，不能让黑客控制了服务器。做法见 [D-0093](decisions/0093-login-and-server-hardening.md)。
  - 限制登录次数别太离谱：人类还是很笨的，输错 20 次也可能是正常人类（作者，2026-11-11）。
- **多用户的设计按「假如有 1 万个用户」来检验**：不会带来过大的代价就行，会就不行（作者，2026-11-11）。数据怎么按用户隔开见 [D-0091](decisions/0091-one-database-per-user.md)。
- **隔离**（作者，2026-11-11，作者理想中的）：
  - **防住子应用的恶意行为**：用户装了一个别人写的恶意子应用，它至少不能冒充其他子应用、去破坏其他子应用的数据。
  - **不防用户自己的恶意行为**：用户理论上拥有他自己的子应用的全部权限；他把平台拆了、让自己的子应用全部大乱炖，我们也没办法。
  - **用户不能影响其他用户**：只要做到这一点即可。
  - agent 注：要做到这几条，子应用的界面和后端都要关起来。界面在浏览器里的做法见 [D-0090](decisions/0090-sandboxed-app-frames.md)；后端现在和内核跑在同一个进程里，技术上能绕过内核（直接读数据库文件等），装别人写的子应用之前要先解决（作者：后端关进沙箱以后再说，现在只有朋友用，问题不大，2026-11-11）。服务器上，凡不是平台自己的代码（包括用户自己写的子应用）都可能影响其他用户，也要关起来；服务器的计算、存储、带宽是大家共用的，也要防一个用户占满。（agent 起初还说平台 AI 要按用户限额——不对：每个用户用自己的 API key，见「平台 AI」。）

## 数据一致性

- 跨应用的一次操作（例：对话里加一个词，同时在学英语应用里落账）**要么全部生效，要么全部不生效**，不能留下半截状态。
- 结构上**不会出现写冲突**，不依赖开发者自觉。
- **一个子应用的公开 API 被很多子应用调用时，不乱是这个子应用自己的事**（作者，2026-11-11）：
  - 作者当初担心：如果每个子应用都把随便什么功能变成公开 API、各路子应用都去调用，就可能发生混乱，指的是**事务层面的写冲突**。
  - 这次放开普通 API（以前叫「普通的异步函数」，[D-0086](decisions/0086-public-async-functions.md)），是因为「下载音乐」本身不是一个事务：两个子应用各自发起下载，不会冲突。但以后可能有的 API 是一个「长事务」，当作普通的异步函数开放，就会导致冲突，而且是内核难以保证的。
  - 现在觉得内核层可能没法保护这一条，还是得子应用自己搞定。
  - **公开 API 必须自己防住并发**（作者，2026-11-11）：不是公开 API 时，防并发是子应用内部的问题，它可以自己在调用层面解决；一旦作为公开 API 发布，防并发就变成这个 API 必须解决的问题——不管别人怎么调，API 都必须能防住。归纳成两条（作者）：
    - **普通 API 得防住并发**；
    - **事务 API 得确保自己作为一个事务是成立的**（作者：事务 API 也要保证自己的安全性，作为一个事务执行的时候不会出现问题）。
    - agent 注：事务执行期间不受别的写入干扰，这一点内核保证；事务 API 自己要做的，是它依据的前提都在事务里核对，不直接相信调用方之前看到的。例：`vocab.addCard` 核对判重之后这个词有没有多出卡片（VOCAB-0010）。
  - **内核的职能是把出问题的范围锁在一个子应用里**：再怎么乱，乱的只是被调用的子应用自己的数据——它写不到调用方的数据，调用方也只能经它的 API 碰它（agent 的说法，作者认可：这确实是一个合理的内核职能，2026-11-11）。

实现见 [D-0004](decisions/0004-sqlite-single-writer-queue.md)、[D-0007](decisions/0007-sync-pure-tx-functions.md)、[D-0008](decisions/0008-resolve-then-commit.md)。

**系统层关于 API 与事务的设计非常重要**：将来各种人都可能 vibe coding 自己的产品，系统的设计格外关键。现行方案（写数据只能通过事务 API，见 [D-0063](decisions/0063-internal-apis-may-be-async-functions.md)；要等外部又要写数据的普通 API 也可以公开，它只写自己的数据，见 [D-0086](decisions/0086-public-async-functions.md)）暂时可行；以后可能修改（例如引入锁机制），目前没有研究新设计的必要。

## 开发时的更新

- 开发中更新某个子应用，**不能靠整机重启**——整机重启会连带重启所有子应用、丢失正在进行的会话（实现见 [D-0017](decisions/0017-per-app-hot-reload.md)，尚未实现）。

## 平台 AI

- AI 是平台提供给各个子应用的**核心能力**，预计多个子应用都会使用。
- **AI 服务的密钥由平台保管，子应用拿不到。**
- **每个用户用自己的 API key**：用户用他自己的 token 驱动他安装的所有子应用；作者的 API key 只是作者自己的（作者，2026-11-11）。现阶段（只分发给朋友，不开放公众注册）这一点还没关系。
- **平台设置**：子应用一般不能修改平台设置，但可以读取（例如界面语言）；API Key 这类**凭据不能读**——外壳也读不到。
- **agent 框架必须是共享的**（agent 框架：构建工作流与 agent 的框架，概念见 `concepts/agent.md`）：对话、哲野以及将来的子应用都会用到工作流或 agent，而且很可能是更复杂的（提供搜索、编辑等能力）。agent 框架要做成共享的能力，**不能每个子应用各写一套**。对 builder 行为边界的硬约束也要在 agent 框架层面实现（见 `principles.md`「约束：软约束与硬约束都要」）。
- **工作流用代码实现**：工作流（workflow）是一套包含 LLM 调用与工具的程序流程。不同子应用需要不同的工作流；共用的能力与协议放进共享的库，库做不到的（密钥、权限、持久任务等）由平台提供。工作流**一定用代码实现**，以库函数或平台 API 作为能力组件；不用图之类的结构化数据来描绘，也不预设几种工作流给子应用挑选。原因：工作流是很通用的事情，自由度很大，不应受框架性的限制；代码是最通用的载体。代码带来的自由度过大、设计与编写更难的问题，由编码 agent 负责编写，没有什么负面影响。
- **通用结构由平台支持**：对话的消息树、哲野式的任务图，都是很通用的结构，与具体子应用无关，平台要把它们作为通用能力提供。二者是两种不同的东西（语义不同：消息树的分支互相替代，任务图的子节点都要完成），可以互相包含。提供方式见 [D-0061](decisions/0061-agent-structures-as-platform-base-classes.md)。
- **类对象是指向数据的把手**：通用结构的类对象，对应的是一套被维护的数据（现在的设计中，长期存储的数据就是数据库里的表）。对象本身不保存数据，只是指向数据的把手——轻量、用完即丢；「当前进行到哪」（例如当前选中的分支）也存在数据里，而不是对象的内存里。因此「恢复」就是新建一个指向同一份数据的把手。
- **对话过程中不改动工具定义**（原则性要求）：同一段对话里，每一次请求带的工具定义都一样。改动会让缓存不命中，也会让模型困惑。需要「这一次不许调用工具」时用别的办法（见 [D-0078](decisions/0078-tools-unchanged-within-conversation.md)）；做不到某个需求时，告诉作者。
- **共享库具体提供哪些能力是细节**：例如工具循环、结构化调用等具体以什么形式提供，不属于上层设计，等子应用实际用到时再定，可以由 agent 自行决定。
- **用量管控**：子应用增多、分发给其他用户（朋友或外来的用户）以后，一定要有**按子应用的、更严格的 token 用量管控与显示**。现阶段开销不高，管控暂不实现；按子应用的用量与花费显示已有（见 [D-0074](decisions/0074-usage-and-cost-display.md)）。
- 当前使用 DeepSeek（见 [D-0014](decisions/0014-deepseek-as-ai-provider.md)）。

## 多端

- 将来要在手机上使用 MyOutside，**个人数据在电脑与手机之间共用**（见 `product.md`「平台」）。云同步是将来才实现的事。
- 当前为此做的准备与选定的方向见 [D-0012](decisions/0012-runtime-agnostic-kernel.md)、[D-0013](decisions/0013-cloud-kernel-for-multi-device.md)、[D-0020](decisions/0020-mobile-via-web-ui.md)。
- **作者买了一台云服务器**（2026-11-11；情况见 `docs/server.md`）。接下来按顺序做这几件事，一件一件来（作者，2026-11-11；作者：我想的不一定周到，觉得有必要在中间做的就说）：
  1. 看一下服务器的配置和基本能力（例如访问外网），简单防御一下黑客攻击（例如关掉一些端口、防火墙策略）；
  2. 研究怎么把 MyOutside 部署上去：这次真的要做到服务端和客户端分离，架构可能大改；
  3. 用户注册登录体系，不同用户的数据独立，方便以后分发给作者的同学；
  - **域名 `myoutside.org`**（作者 2026-11-11 在 Cloudflare 买的）：这就是 MyOutside 的正式域名，以后提供公开 SaaS 服务也可以用（作者，2026-11-11）。DNS 的设置见 [D-0088](decisions/0088-domain-dns.md)。
  4. 纯蓝这类东西肯定是跑在本地的，所以 MyOutside 需要有一个良好的多设备处理方式。
- **设备**：用户的电脑是一台设备（概念见 `concepts/structure.md`「设备」）。将来 MyOutside 在云端，用户的电脑是连到它上面的设备。
  - 设备上的数据就放在设备上。例如用 MyOutside 做科研：科研文件夹很大，就是用户电脑上的一个普通文件夹，MyOutside 和电脑上的其他程序（git、PyTorch……）都可以正常访问，不需要 MyOutside 限制它的访问边界。
  - 子应用访问设备需要授权（在清单里登记），并且要有内核与设备之间的通道（见 [D-0080](decisions/0080-device-access.md)）。

## 未定

- **安装即常驻**：是预期，但还没有一个清晰明确的理由。
- **公开 API 的两条约束怎么保证**（「数据一致性」：普通 API 得防住并发，事务 API 得确保自己作为一个事务是成立的）：显然没办法机械保证。但现在是一个充满智能的时代，也许可以引入 LLM 或者 workflow 进行机械检查之类的；这个问题有点远，暂时没想好，以后再说（作者，2026-11-11）。
- **通用结构**：是否存在能把消息树与任务图统一起来的更好设计，作者还没想明白；现阶段当作两种东西。
- **数据的底线要求**（能否导出带走、存在哪里等）：暂不考虑——现在的数据体系是临时版本，还没有用户体系，也没有跨设备的云端同步。
- **数据恢复**（误删、或 builder / 临时函数改坏数据后能否恢复）：暂不考虑，但**很重要，以后要思考**。可能与 `principles.md`「硬约束是保底」相关。
- **主页像移动端桌面**：MyOutside 的主页类似手机桌面，每个子应用一个圆角矩形图标，点击打开子应用。只是一个 UI 层面的想法，尚不完善（早期文档中称为「模拟器式界面」，目前未实现）。
