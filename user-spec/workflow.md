# 开发方式

## user spec 与决策

- 本项目按 user spec 的方式开发：用户的预期写在 `user-spec/`，实现上的选择记为决策（见 `README.md`）。
- 编码 agent 动手前先读 user spec，动手后记录决策（见仓库根目录 `AGENTS.md`）。

## 和 agent 的合作方式

### 基本认识

- 人类的认知带宽是重要的瓶颈，**开发进度不应该完全被人类的认知带宽卡住**。作者相信 agent 能提出好的设计、写出好的代码。
- 作者是 CS 技术背景，能理解大部分技术概念，但不会深究每一处设计与实现。

### 作者做什么

- **提供预期**：想要什么、什么重要、什么不要——用自己的话说即可，翻译成 spec 与决策是 agent 的事。
- **决策**：需要上层决策的事，作者觉得重要的，会理解明白再决策。
- **使用与反馈**：agent 推进过程中的汇报，作者可以不完全理解；等产品用起来，自然会产生想法和修改意见。
- **保持怀疑**：觉得不对劲时追问"这真的需要吗？""为什么这么复杂？"。
- **守住连续性**：agent 没有跨会话的记忆；作者与 user spec 是项目的连续性所在。

### agent 怎么汇报

以下规则只适用于 agent 与作者的**对话**；文档里只写实打实的内容，不使用这些标记。

- **每件事标明需要作者做什么**：
  - 🔴 **需要作者决策、同意或理解**——必须醒目标出，并说明会产生什么影响；
  - 🟡 只需知道；
  - ⚪ 不用管（已记为决策）。
- 作者最困惑的场景是：agent 说了一堆，作者不能完全理解，**也不知道会产生什么影响**。所以：
  - 讲解时**尽量一同讲清后果**（作者会感受到什么、以后能不能改），不要纯讲抽象的内部概念；技术术语可以用。
  - 难以回头的决策（例如数据模型、内核语义、安全边界）与作者每天会直接感受到的体验，优先标 🔴。
- 🟢 **修改了 user spec 时**（不含 `decisions/`）：在回答末尾用 🟢 简要说明改了哪些地方。
- 决策记录保持现在的写法（作者认为易读）。

### 节奏

- 实现速度已经足够快；**把设计做好非常重要**，不要为了速度牺牲设计。

## 当前阶段的节奏

- **现阶段先推进实用的功能和 demo。**
- 文档与代码之间的细节不一致，暂时不管。

## 不能破坏作者的生活数据

- 开发、测试过程**不能破坏作者的真实数据**——这些数据是作者生活的一部分。
- 用什么方式保证（例如临时数据副本、假数据）不做要求（当前做法见 [D-0046](decisions/0046-smoke-on-temp-data-copy.md)）。

## 语言

- 文档用中文写。

## 工程规范

- 没有特别的要求。当前的规范见 [D-0044](decisions/0044-docs-sync-with-features.md)、[D-0045](decisions/0045-commit-and-test-conventions.md)。

## 冲突处理

- 需求层次上的冲突（例如服务个人生活与产品化之间），把冲突的原因告诉用户，由用户决定（见 `product.md`「双重使命」）。
