# user spec：用户的预期层

> 状态：概念设计（2026-10-21）。作为 MyOutside 提供给用户的产品能力，尚未实现。
> 这是「新时代 vibe coding 方式」的核心概念之一：把**用户的预期**从 agent 的文档与实现中独立出来，成为持续维护的一层。
> 本项目自身的开发已经采用这一方式：spec 文档 + 决策（decisions）两层，规则见 `user-spec/README.md`。

## 1. 问题：vibe coding 循环会漂移

当前的协作循环大致是：

```
人提出粗糙需求 → agent 实现 → 人反馈 → agent 调整 → …
```

单次循环是收敛的：agent 越改越符合人当下的反馈。但跑久了会出问题：

1. **agent 分不清"用户关注的重点"和"自己选择的实现"**——它可能把用户在意的东西当成可随意改动的实现细节（拆东墙补西墙）；也可能把现状当成用户预期，不敢推翻自己的旧实现；
2. **人的预期没有被显式沉淀**——需求只存在于一轮轮对话里，人自己也会忘；重新理解自己的项目越来越难；
3. **文档无法替代**——文档是 agent 的理解与实现细节，又长又细；人不会读完，也不应该读完。

## 2. 定义

**user spec = spec ∩ user thought**：

- 是**能作为规格成立**的内容（可以指导实现、可以拿来评审）；
- 同时是**用户真正在意**的内容（人觉得随便的东西不在此列）。

它不是聊天记录，不是技术文档，也不是现状快照。它记录的是**用户的预期**；现状在代码与文档里，两者之差就是当前要做的事。

**它是源，不是派生物**：

```
user spec（用户的预期；源）
   ↓ 派生
技术 spec / 文档 / 代码 / 测试（agent 的理解与实现；可再生）
```

冲突时向上收敛：以 user spec 为准；派生物可以随时重写。

## 3. 两个读者，两个作用

### 3.1 对 agent：变更许可边界

- **spec 之内 = 承重墙**：这是用户的预期。agent 不能自作主张改；要动，就等于"用户在推翻自己"，必须回来讨论。
- **spec 之外 = 自由区**：现状与实现方式。agent 可以大胆推翻、重构、重写，不必对现状忠诚。
- 这一条同时治两个病：
  - 拆东墙补西墙——不知道哪面墙承重；
  - 不敢推翻自己——把现状误当成预期。
- 遇到冲突时，正确的反应不是"覆盖旧需求"，而是停下来问：**"是我理解错了，还是你改主意了？"**

### 3.2 对人：重读自己的入口

- 用户忘记产品定位或想法时，翻 user spec，而不是翻文档；
- 文档是给 agent 的（长、细、可执行）；user spec 是给人的（原话、短、熟悉、能翻）；
- 收录标准：**用户会不会在意、能不能认出自己**。不会的，不属于这一层。

## 4. 它不是什么

- 不是聊天记录——噪音太多，且人不会读完所有 agent 回复；
- 不是技术文档——那是 agent 的理解、细节与契约；
- 不是现状描述——现状可以变，预期才是边界；
- 不是石碑——用户可以推翻自己，但那是**显式事件**（需要讨论与确认），不是 agent 的静默修订。

## 5. 生长方式

- 从**人与 agent 的交互过程**中沉淀：人主动提出、人认可 agent 的提议、人纠正偏差、人在方案中做选择；
- 可以像文档层一样不断增长，不要求"必须很小"；
- **维护权可以交给 agent**：整理、去重、合并、挂锚点、更新状态、从对话中起草候选；
- 但**权威来源是用户**：agent 写的是"关于用户的事"，不能"以用户的名义想事情"；"这确实是我想要的"必须由人确认。
- 暂定红线：新增与语义变更需用户确认；纯整理（不改含义、合并重复、挂锚点、更新状态）agent 可以自治。

## 6. 与其它层的关系

| 层 | 内容 | 读者 | 生命周期 |
|---|---|---|---|
| **user spec** | 用户的预期 | 人（以及 agent 对照） | 只追加 / 标记取代；不可再生 |
| 技术 spec / 文档 | agent 的理解与实现细节 | agent | 可重写、压缩、重新生成 |
| 代码 / 测试 | 现状 | 机器 | 可重构 |

- 文档层可以重写十遍仍忠于同一个 user spec；user spec 一旦丢失，重新生成的"项目"就是另一个项目；
- user spec 应保留历史：旧想法可以被取代，但不应被悄悄抹掉——"用户改主意"本身是重要信息。

## 7. 判定与检验

一条内容是否属于 user spec：

1. 用户在意吗？
2. 它能作为规格指导实现或评审吗？
3. 用户重读时认得出自己吗？

成功状态一句话：**agent 在 spec 外自由、在 spec 内请示；人在 spec 里认出自己。**

## 8. 与 MyOutside 的关系（暂定）

- 它天然是**主框架级**的数据（不属于任何单一子应用）；
- builder 的主要职责是 vibe coding（建立、修改子应用），它要服从「user spec 层 + 技术实现层」的层级设计（见 `builder.md`）；
- user spec 是"新 vibe coding 方式"的题眼之一：agent 负责让现状向预期收敛，人负责提供预期与认可。

## 9. 开放问题

- 锚定粒度：功能点 / 模块 / 代码位置？
- 形态：只追加的账本 + 派生视图，还是允许持续改写的当前规格？（倾向前者，未定）
- 冲突时的交互：提醒、阻塞，还是准备两版方案供选择？
- agent 维护的自治边界（纯整理 vs 语义变更）具体怎么划？
- 在 MyOutside 中的实现时机与形态（builder 的组成部分？平台数据域？）。

## 10. 本项目的实践（2026-10-21）

本项目自身开发时对上述问题的回答（作为产品功能时可以参考，但不必照搬）：

- **两层**：spec 文档（作者的预期，以高层次为主，正常文档形式）+ 决策（连接预期与实现，记录为什么这样实现、考虑过什么、何时重新考虑）。spec 文档提及实现时必须引用决策。
- **形态**：spec 文档是当前规格，按主题分文件；历史靠决策的状态（已取代 / 已废弃）与 git 保存。
- **自治边界**：新增与语义变更需作者确认；纯整理 agent 可以自治；决策 agent 可以自由记录，并鼓励在符合预期的前提下推翻。
- **与 `requirements.md` 的关系**：已拆分进 spec 文档与决策，原文件删除；`docs/` 明确为技术文档层。
