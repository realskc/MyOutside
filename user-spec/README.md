# MyOutside user spec

这个目录记录**作者对 MyOutside 的预期**——MyOutside 的 user spec 就是作者的意志。它是整个项目的源头：技术文档、代码、测试都是为了满足这里的预期而存在的派生物。

> ⚠️ **用词约定**：「作者」指掌控 MyOutside 设计与定位的项目作者本人；「用户」指使用 MyOutside 产品的人。agent 领域里常把「和 agent 对话的人」叫用户——在本项目里，这个人叫「作者」。指项目作者本人时请写「作者」（概念见 `concepts/actors.md`）。

概念来源：`future/user-spec.md`（user spec 作为 MyOutside 产品功能的设计）。本目录是这个概念在本项目自身开发中的落地。

**仓库根目录的 [AGENTS.md](../AGENTS.md) 也属于 user spec**：它是作者对开发方式、对 agent 怎么参与开发的预期，只是位置不在本目录——放在根目录，agent 工具开工时会自动读到。只看 user spec 重构项目时，范围是本目录加上 AGENTS.md。

## 记录标准

内容忠实于作者的意志，表达和组织由 agent 负责；**主动整理成连贯、独立可读的文档是 agent 的职责**。（作者确认，2026-11-12）

- 默认用正常语言转述，合并重复表达，把多轮对话中的同一主题组织在一起，展开依赖上下文的指代。作者补充想法时融入已有内容，不逐条堆积问答。
- 整理的边界是含义：保留作者要什么、为什么在意、明确不要什么，以及范围、前提、例外、要求强弱和确定程度。结合上下文意思明确即可整理，不要求作者像写合同一样表达。不得新增理由、替作者取舍或在不同解释中擅自选一种；实际工作需要解决时再讨论。
- 原话按价值保留：措辞承载重要态度、比喻或个人表达，作者明确要求保留，或转述容易把尚未明确的想法定死时，保留原话并融入主题叙述。「先做到这些就行」可以整理为「当前先支持这些能力即可」，不能变成永久性的「产品只支持这些能力」。
- 正文按主题记录当前预期。一次性的工作指令、确认过程和材料处理经过，按用途归入合作规则、决策或历史说明，不因作者说过就逐条收入总览。日期和来源标在有用的位置，例如一组预期的出处或一次立场变化，不必逐句重复。
- 忠实转述属于正文，不标成「agent 注」；agent 额外提出的解释、推断或联想才用这个标记。
- 检查时同时核对忠实性和可读性：每项预期的含义有作者表达或认可的依据，文档脱离原会话也能读懂。不要求正文与聊天原句一一对应。

## 两层内容

### 1. spec 文档（本目录下除 `decisions/` 以外的文档）

- 用正常文档的形式叙述**作者的预期**：产品是什么、为谁服务、什么重要、什么不要、谁不能访问什么。
- 以高层次的预期为主。作者通常关心"要达到什么"，而不关心"具体怎么实现"。
- 可以提及具体实现——有时具体实现确实重要——但提及时**必须附上对应的决策**（如"……（见 [D-0001](decisions/0001-one-off-functions.md)）"），表明这是基于决策的方案，**不与作者预期处于同一层次**。
- 正在思考、尚未定论的内容同样重要：写在各文档的「未定」一节，与已确认的预期分开。

**读法**：spec 文档中未引用决策的叙述 = 作者的预期 = 承重墙。要改动它，等于作者推翻自己，必须先与作者讨论。

### 2. 决策（`decisions/`）

- 一条决策连接**作者的预期**与**具体的实现**：记录当时为什么这样做、经过了怎样的思考、考虑过哪些方案、为什么没有采用。
- "不用 xxx"同样是决策。
- 决策**可以被推翻**，而且**在符合作者预期的前提下，我们鼓励推翻**：有更合理的改进方案，或环境发生重大变化时，就选择另一种实现——推翻的方式是写一条新决策取代旧决策，而不是删除。很多决策本身就是随手的选择，会如实标注「随时可以」重新考虑。
- 决策不要求作者看过。它的价值是**记录与溯源**：将来想了解历史或推翻时，能知道哪些是作者的预期，哪些是当时思考出来的方案。
- **全局/跨应用决策**放在 `decisions/`，编号 `D-NNNN`；**应用专属决策**放在 `apps/<app>/user-spec/decisions/`，编号 `<APP>-NNNN`（如 `GO-0001`），由应用自己的 `user-spec/README.md` 与决策索引维护。
- **应用专属 user spec** 也放在 `apps/<app>/user-spec/`，与 decisions 一起（[D-0073](decisions/0073-app-local-decisions.md)）。
- 写法与模板见 [decisions/README.md](decisions/README.md)；应用决策沿用同一模板。

## 引用关系

```
spec 文档（作者的预期）
   ↑ 服务于
决策（为什么这样实现）
   ↑ 引用
技术文档 / 代码注释（怎么实现）
```

- spec 文档提及实现时引用决策；
- 技术文档（`docs/`）、代码注释等**一切文档**都可以引用决策作为设计依据；
- 决策可以引用上游决策（例如"选 SQLite"服务于"内核是唯一写入者"这条决策）。推翻上游决策时，沿引用链检查下游决策是否需要一并重新考虑。
- 目标：user spec 像 user spec，技术文档像技术文档，二者通过决策良好地连接。

## 变更规则

| 变更 | 谁可以做 |
|---|---|
| spec 文档：新增预期、改变已有预期的含义 | 必须由作者提出或确认 |
| spec 文档：纯整理（不改含义的措辞调整、合并重复、补引用、更新状态） | agent 可以自行完成 |
| spec 文档：「未定」一节记录讨论中的想法 | agent 可以起草，标明尚未确认 |
| 决策：新增 | agent 可以自行记录（**建议**：凡是基于作者需求做出的实现决定都记下来） |
| 决策：推翻（换了方案、方向反转） | 写新决策取代旧决策，并标注旧决策状态；若取代会改变 spec 文档中的叙述，按 spec 规则处理 |
| 决策：小的修改，或修改刚定下的决策 | 原位修改；有非平凡理由时在决策末尾写「修订记录」（见 `decisions/README.md`） |

agent 发现 spec 与需求或现状冲突时，正确的反应不是覆盖，而是停下来问：**"是我理解错了，还是你改主意了？"**

### 作者亲自规定的细节

作者通常不关心实现细节。如果作者人为规定了某个细节，背后很可能有更高层次的考量：

- 细节本身记为决策，**决策者 = 作者**；
- 背后的高层次考量写进 spec 文档（不清楚时问作者），并让该决策引用它。

这样将来推翻这个细节时，能知道它当初是为了满足什么。

## 给 agent：遇到"重构"类需求时

1. 先读 spec 文档，确认哪些是作者的预期（不能变）；
2. 再读相关决策，了解现有实现服务于哪些预期、当时排除了哪些方案、什么条件下应重新考虑；
3. 在满足作者预期的前提下，决策层的一切都可以重新选择——可以并且应该提出结构性优化的建议；
4. 推翻决策时写新决策，说明取代了哪条、为什么。
